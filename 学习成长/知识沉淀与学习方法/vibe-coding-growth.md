## 一、什么是 Vibe Coding？

### 1.1 定义

**Vibe Coding** 是一种以AI为核心协作伙伴的编程方式——人不写具体代码，而是通过描述需求、拆解任务、把控质量，让AI完成具体的编码工作。

人的角色从"写代码的人"变成了"产品经理+项目经理+质量总监"：
- **产品经理**：定义做什么、为什么做、做成什么样
- **项目经理**：拆解任务、排优先级、协调多个AI角色
- **质量总监**：验收标准、测试验证、把控质量底线

### 1.2 跟传统编程的区别

| 维度 | 传统编程 | Vibe Coding |
|------|---------|------------|
| 人的角色 | 执行者（写代码） | 指挥者（定方向+把质量） |
| 代码产出 | 人一行行写 | AI生成，人审核 |
| 效率瓶颈 | 人的编码速度 | 人的需求清晰度和判断力 |
| 核心能力 | 语法熟练度、编码技巧 | 需求拆解、质量把控、问题定位 |
| 学习曲线 | 先慢后快（语法入门难） | 先快后深（上手快，精通难） |

### 1.3 为什么Vibe Coding很重要？

- **效率提升**：一个人能干一个小团队的活（前端+后端+测试+运维）
- **门槛降低**：不需要精通每门语言和框架，就能做出完整的产品
- **角色升级**：从"写代码的人"变成"定义产品的人"
- **未来趋势**：AI写代码的能力只会越来越强，人的价值越来越体现在判断和方向上

## 二、我的 Vibe Coding 成长轨迹

> 不是一蹴而就的，是踩了很多坑、迭代了很多次才到今天这个水平的。

### 阶段1：单AI全干（初始期）

**时间**：最开始做项目的时候

**工作方式**：
- 把所有需求丢给一个AI，让它从头到尾全做了
- "帮我做一个穿搭网站，前端React，后端Python"

**遇到的问题**：
- 生成的代码质量不稳定，经常有bug
- 一次改太多，出了问题不知道是哪里改坏的
- 验收靠肉眼看，"感觉能跑就行"
- 改了几次之后，AI开始乱了，前后不一致

**能力水平**：⭐⭐
- 能用AI做出东西，但质量不可控
- 效率不一定比自己写高，因为调试花很多时间

**标志性痛点**：
> "AI写的代码，我得花一半时间改bug。到底是提效了还是降效了？"

---

### 阶段2：多角色分工（进阶期）

**时间**：穿搭项目中期

**关键认知突破**：
> 一个AI干所有活，就像一个人又当前端又当后端又做测试——什么都做了，但什么都不精。
> 为什么不让不同的AI扮演不同的角色？就像真实的团队一样。

**工作方式升级**：
- 拆成**前端专家**、**后端专家**、**测试专家**三个角色
- 每个角色只做自己擅长的事
- 人来做PM和QA：拆解任务、分配工作、最终验收

**具体做法**：
- 前端任务交给"前端专家"——React、TypeScript、Tailwind CSS
- 后端任务交给"后端专家"——Python、FastAPI、大模型调用
- 测试任务交给"测试专家"——写测试用例、做验收
- 我自己负责：需求定义、任务拆解、优先级排序、质量把关

**效果提升**：
- 代码质量明显提高——每个领域的AI更专业
- 出了问题容易定位——是前端的问题还是后端的问题，一目了然
- 效率提升了——可以并行做不同的任务

**能力水平**：⭐⭐⭐
- 知道怎么跟AI协作了，不再是"一句话全丢给它"
- 会拆任务了，知道什么任务该给什么角色

**标志性事件**：
> "发现拆成三个角色之后，代码质量上去了，调试时间少了很多。原来不是AI不行，是我用AI的方式不对。"

---

### 阶段3：断言驱动 + 任务卡体系（成熟期）

**时间**：穿搭项目中后期

**关键认知突破**：
> 光靠人眼验收不行——人会漏，而且每次验收标准不一样。
> 必须有**客观的、可重复的验收标准**——就是断言（assertion）。

**工作方式再次升级**：

#### 3.1 任务卡体系
- 每个迭代单元做成一张**任务卡**
- 一张卡只做一件事，做完就commit
- 任务卡包含：做什么、为什么做、验收标准是什么
- 总共做了**31张任务卡**，覆盖从Phase 0到Phase 15+

#### 3.2 断言驱动验收
- 每个功能写完，必须有对应的测试断言
- 不是"看起来对"，而是"跑测试全绿"
- 断言数量从0增长到**627条**（28个验收脚本）
- 用变异测试验证断言的有效性——"断言能不能真的测出bug"

#### 3.3 黄金集回归
- 建立一套固定的"黄金测试集"
- 每次改完代码，都用黄金集跑一遍
- 确保新改动不会把旧功能搞坏（回归测试）
- 三层质量门禁：Gate1 / Gate2 / Gate3

**效果数据**：
- 二调成功率：<30% → **100%**（第一次交付出错了，第二次调完必过）
- 首调Token消耗：**-22%**
- 首调耗时：**-29%**
- 从0到1的验证周期：月级 → **周级**

**能力水平**：⭐⭐⭐⭐
- 有完整的工作方法论了，不再是"凭感觉"
- 质量可控，效率可衡量
- 能系统性地迭代优化

**标志性事件**：
> "当断言数到500+的时候，我突然觉得心里有底了——改代码不怕改坏，因为跑一遍测试就知道有没有问题。"

---

### 阶段4：方法论沉淀 + 技能团审计（精通期）

**时间**：项目后期到现在

**关键认知突破**：
> 好的方法不能只存在脑子里，要写下来、固化成文档。
> 而且，光靠一个测试专家验收还不够——多角色交叉审计，质量更有保障。

**工作方式继续升级**：

#### 4.1 方法论文档化
- **AGENTS.md**：项目级AI工作手册（1800+行，36条工程约定，28个验收脚本，627条断言总表）
- **project-rules.md**：10条NEVER规则 + 10条ALWAYS规则 + 验收决策表
- **product-lessons.md**：7大类32条产品经验积累
- **任务卡体系**：31个迭代单元的完整记录

#### 4.2 技能团并行审计
- 从"一个测试专家验收"升级为"多角色并行审计"
- 五个角色同时审：前端、后端、数据契约、用户旅程、埋点
- 每个角色从自己的角度找问题
- 比如："每站各自绿 ≠ 旅程通"——跨站的漏斗断裂，单站验收全绿也发现不了

#### 4.3 自我质疑式设计
- 不是"我觉得对就这么做"
- 而是故意推翻自己的结论，重新审视
- 比如：设计综合v3推翻了v2的三个核心结论
- 推翻之后重新设计，方案更扎实了

**能力水平**：⭐⭐⭐⭐⭐
- 有完整的、可复用的方法论
- 不仅会用AI写代码，还会优化AI的工作方式
- 能把经验沉淀下来，越做越快，越做越好

**标志性事件**：
> "当我把AGENTS.md写完的时候，我意识到——我不只是在用AI做项目，我还在创造一套用AI做项目的方法。"

## 三、Vibe Coding 能力的5个维度

### 维度1：需求拆解能力

**是什么**：把一个模糊的大需求，拆成AI能理解、能执行的小任务。

**为什么重要**：
- AI不擅长处理模糊的需求
- 需求拆得越细，AI做出来的东西越靠谱
- 拆得不好，AI会理解偏差，做出来的东西不是你要的

**你的水平**：⭐⭐⭐⭐⭐
- 31张任务卡，每张卡只做一件事
- 知道怎么拆、拆到什么粒度
- 拆之前会先做术语对齐——确保你说的词和AI理解的是一个东西

---

### 维度2：质量把控能力

**是什么**：怎么保证AI写出来的代码是对的、是稳定的。

**为什么重要**：
- AI会犯低级错误
- 只靠人眼验收，漏的太多
- 没有质量保证，改代码就是玩火——不知道什么时候就把旧功能搞坏了

**你的水平**：⭐⭐⭐⭐⭐
- 627条断言，28个验收脚本
- 变异测试验证断言有效性
- 黄金集回归测试（三层门禁）
- 技能团多角色并行审计

---

### 维度3：问题定位能力

**是什么**：AI写的代码出了问题，能不能快速找到原因、解决掉。

**为什么重要**：
- AI写的代码，不一定是你熟悉的写法
- 出了问题，如果看不懂、不会调，那还不如自己写
- 定位问题的速度，直接影响迭代效率

**你的水平**：⭐⭐⭐⭐
- 熟悉自己项目的代码结构（因为是你拆的任务，你知道每块代码在哪）
- 有完整的日志和错误信息
- 会用"代码对质"——讨论问题之前，先去看代码到底是怎么写的
- 有归因分析方法论——不是猜，而是系统性地找根因

---

### 维度4：AI协作能力

**是什么**：怎么跟AI高效协作，让AI发挥最大价值。

**为什么重要**：
- 同样的AI，不同的人用，效果天差地别
- 会用AI的人，效率是不会用的人的好几倍
- 这是一种新的核心能力——就像20年前会不会用电脑一样

**你的水平**：⭐⭐⭐⭐⭐
- 多角色分工协作（前端/后端/测试专家）
- 有完整的Prompt和指令体系（AGENTS.md）
- 知道AI擅长什么、不擅长什么
- 会用AI做调研、写文档、做分析——不只是写代码

---

### 维度5：方法论沉淀能力

**是什么**：能不能从实践中总结经验，形成可复用的方法论。

**为什么重要**：
- 踩过的坑不能白踩
- 有方法论，才能越做越快、越做越好
- 这是区分"熟练工"和"专家"的关键

**你的水平**：⭐⭐⭐⭐⭐
- AGENTS.md：完整的AI项目工作手册
- project-rules.md：20条核心规则
- product-lessons.md：7大类32条产品经验
- 任务卡体系：可复用的迭代管理方法

## 五、我的 Vibe Coding 方法论

### 5.1 核心原则

1. **任务拆细**：一张卡只做一件事，做完就能验证
2. **断言先行**：先想清楚怎么验收，再开始做
3. **术语对齐**：先把词对准了，再讨论需求
4. **代码对质**：讨论问题之前，先看代码到底是怎么写的
5. **数据说话**：能用数据验证的，就不凭感觉
6. **小步快跑**：快速迭代，快速验证，不行就改

### 5.2 工作流程

```
1. 需求澄清
   ↓
2. 术语对齐（确保理解一致）
   ↓
3. 任务拆解（拆成独立可验证的小任务）
   ↓
4. 写任务卡（做什么/为什么/验收标准）
   ↓
5. 分配给对应AI角色（前端/后端/测试）
   ↓
6. AI执行，人监控（不插手细节，但要知道进展）
   ↓
7. 验收测试（跑断言、跑黄金集）
   ↓
8. 有问题 → 定位原因 → 再迭代
   ↓
9. 没问题 → commit → 下一张卡
```

### 5.3 验证链（从直觉到决策）

> **直觉 → 术语对齐 → 代码对质 → 联网调研 → 低成本实验 → 数据拍板**

- 直觉是起点，不是终点
- 每一步都要验证，不能跳步
- 最终决策必须有数据支撑

## 六、Vibe Coding 和 AI产品经理的关系

### 为什么AI产品经理要会Vibe Coding？

1. **快速验证想法**：有了产品想法，自己就能搭原型验证，不用等开发排期
2. **更好的技术判断力**：自己做过全栈项目，跟开发沟通的时候不会鸡同鸭讲
3. **更懂AI的边界**：天天跟AI协作，自然知道AI擅长什么、不擅长什么
4. **更高的效率**：一个人就能干一个小团队的活，从想法到原型，几天搞定
5. **未来的核心竞争力**：AI时代的产品经理，不会用AI做产品，就像现在的产品经理不会用Axure一样

### 你的优势是什么？

- 你**不是只会用AI的产品经理**，你是**用AI做出了两个完整项目的产品经理**
- 你**不只是"让AI写代码"**，你有**完整的方法论和质量体系**
- 你**不是停留在概念层面**，你有**具体的数据和成果**
- 你**不只是用AI工具**，你在**创造用AI的方法**
