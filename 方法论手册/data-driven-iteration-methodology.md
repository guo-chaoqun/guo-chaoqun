# 数据驱动迭代方法论 · 操作手册

> 生成日期：2026.10.06
> 来源：电商客服RAG评测项目 + AI穿搭导购项目（97份文档提炼）
> 定位：可复用的操作手册——下一个项目直接照着做，迭代效率翻倍

## 为什么要数据驱动？

很多人做产品迭代是"拍脑袋"的——

- "我觉得这个功能应该加"

- "用户应该会喜欢"

- "竞品都有，我们也得有"

结果呢？做了很多功能，用户没什么反应，数据也没什么变化。时间花了，精力投了，但不知道值不值。

**数据驱动的核心不是"用数据"，而是"用数据验证假设"。**

> 你有一个想法 → 这是假设
> 用数据验证一下 → 假设成立了吗？
> 成立 → 继续投入
> 不成立 → 赶紧换方向，别在错误的路上越走越远

**没有数据验证的迭代，就是在赌博——你不知道自己是做对了，还是运气好。**

## 一、迭代飞轮：数据驱动的核心模型

### 1.1 Bad Case 驱动迭代飞轮

这是AI产品迭代的核心模型——**用Bad Case驱动，而不是用"想法"驱动。**

```
┌──────────────┐
│  Bad Case采集 │  ←  用户反馈、日志埋点、人工抽检、评测发现
└──────┬───────┘
       ↓
┌──────────────┐
│  归因分析     │  ←  为什么会错？根因是什么？哪类问题最多？
└──────┬───────┘
       ↓
┌──────────────┐
│  优先级排序   │  ←  影响面 × 修复难度 → 先做什么后做什么
└──────┬───────┘
       ↓
┌──────────────┐
│  优化实施     │  ←  针对性优化，一次解决一类问题
└──────┬───────┘
       ↓
┌──────────────┐
│  效果验证     │  ←  A/B测试、前后对比、黄金集回归
└──────┬───────┘
       ↓
┌──────────────┐
│  新Bad Case   │  ←  继续发现新问题，进入下一轮
└──────┬───────┘
       │
       └──────────  循环往复，越转越快  ──────────┘
```

**为什么叫"飞轮"？**

- 每转一圈，产品就变好一点

- 每转一圈，你对系统的理解就深一点

- 每转一圈，你的工具和方法就完善一点

- 转得越多，转得越快——因为你有了更好的工具、更深的理解

### 1.2 跟"需求驱动"的区别

| 维度   | 需求驱动       | Bad Case驱动        |
| ---- | ---------- | ----------------- |
| 起点   | "我想做什么"    | "哪里出了问题"          |
| 方向   | 往前看（加新功能）  | 往下看（修旧问题）         |
| 验证   | 上线了看用户反应   | 优化前后对比数据          |
| 风险   | 做了没人用，浪费资源 | 方向明确，每一次优化都有确定的收益 |
| 适合阶段 | 产品早期，探索方向  | 产品有基础，精细化优化       |

**不是说需求驱动不好，而是——**

- 早期：需求驱动多一些，先把骨架搭起来

- 中期：Bad Case驱动多一些，精细化打磨

- 成熟产品：两者结合——既修问题，也加新功能

**核心原则**：

> **产品有了基础能力之后，修问题比加功能更值钱。**
>
> 因为修问题的收益是确定的——你知道问题在哪，修好了就有改善。
> 加功能的收益是不确定的——你不知道用户会不会用、用了会不会喜欢。

## 二、第一步：Bad Case 采集

### 2.1 Bad Case 从哪来？

| 来源       | 说明                   | 优点           | 缺点                         |
| -------- | -------------------- | ------------ | -------------------------- |
| **评测发现** | 跑评测用例，没通过的就是Bad Case | 系统化、覆盖全面、可量化 | 需要先有评测体系                   |
| **用户反馈** | 用户投诉、差评、客服记录         | 真实、代表真实痛点    | 零散、抽样偏差                    |
| **日志埋点** | 错误日志、异常数据、关键指标下降     | 全自动、覆盖所有用户   | 需要埋点体系，只能发现"出问题了"，不知道"为什么" |
| **人工抽检** | 定期抽一些结果人工看           | 能发现评测没覆盖的问题  | 慢、贵、抽样少                    |
| **内部使用** | 自己天天用，遇到问题记下来        | 零成本、感受真实     | 你不是典型用户，你的问题可能不是用户的问题      |

**最佳实践：多管齐下**

- 评测是主力——系统化、可量化

- 用户反馈和日志是补充——发现评测没覆盖的问题

- 人工抽检是校准——验证评测体系靠不靠谱

### 2.2 怎么采集才有用？

不是把"出错了"记下来就行。好的Bad Case采集，要记录这些信息：

| 字段       | 说明                   | 为+什么重要      |
| -------- | -------------------- | ----------- |
| **输入**   | 用户问了什么/做了什么          | 知道触发条件，才能复现 |
| **实际输出** | 系统返回了什么              | 知道错成什么样了    |
| **预期输出** | 正确的应该是什么             | 知道差距在哪      |
| **问题类型** | 属于哪类问题（幻觉/遗漏/路由错误……） | 方便后续统计分类    |
| **严重程度** | 严重/一般/轻微             | 排优先级用       |
| **来源**   | 怎么发现的（评测/用户反馈/日志……）  | 知道数据来源的可信度  |
| **发生频率** | 出现了多少次               | 估算影响面       |

**反例**：

> "今天遇到一个bug，回答错了。" —— 错在哪？怎么错的？什么时候错的？完全不知道。

**正例**：

> "用户问'退款需要多久'，系统回答'7天无理由退换'——路由错了，分到了退换货规则，没分到退款时效。评测里类似的问题有43条都错了，占失败用例的30%。"

### 2.3 建立"事故疫苗库"

每修一个Bug，就把这个Bad Case加入测试集。

**为什么叫"疫苗"？**

- 疫苗：用少量灭活病毒，让身体产生抗体，以后就不会生病了

- 回归测试集：用已经修过的Bad Case做测试，以后改代码就不会再犯同样的错

**实战方法**：

- 修完一个Bug → 写一条对应的测试用例 → 加入黄金集

- 以后每次改代码，都跑一遍黄金集

- 如果这条用例又红了——说明你把修好的问题又搞坏了（回归）

**这就是为什么成熟的产品，测试集会越来越大——因为每修一个问题，就加一支"疫苗"。**

## 三、第二步：失败归因分析

### 3.1 归因是什么？

知道"通过率是90%"还不够，你还要知道"那10%是为什么错的"。

**归因就是给失败分类——每条失败用例，是什么原因导致的？哪类原因最多？**

- 如果80%的失败都是同一类问题——那把这个问题解决了，就能提升一大截

- 如果失败很分散，什么原因都有——那就得一个个来，没有捷径

### 3.2 怎么设计分类体系？

**原则：MECE（相互独立，完全穷尽）**

- 相互独立：一条失败用例，只能归到一类，不能同时属于两类

- 完全穷尽：所有失败用例，都能找到对应的类别，没有"其他"

**设计步骤**：

1. 先拿20-30条失败用例，手动分类看看
2. 看看大概有几类原因
3. 设计初始的分类体系（3-5类起步）
4. 用更多用例验证，调整分类（合并、拆分、新增）
5. 最终稳定在5-10类比较合适

**别一上来就搞十几二十类——太多了反而不好用。**

### 3.3 实战案例：RAG系统的三层失败模型

这是RAG系统归因的经典框架——按技术栈分层：

```
用户提问 → 检索 → 上下文组装 → 生成 → 回答
            ↓         ↓          ↓
         L1失败    L2失败     L3失败
        （没找到） （找错了）  （不会说）
```

| 层级          | 失败类型             | 表现               | 优化方向                 |
| ----------- | ---------------- | ---------------- | -------------------- |
| **L1 检索层**  | 检索不到 / 知识库为空     | 系统说"我不知道"        | 补充知识库、优化切片           |
| **L2 上下文层** | 路由错误 / 检索不准      | 回答了，但答的是另一个问题的答案 | 优化分类器、优化检索策略         |
| **L3 生成层**  | 幻觉 / 表述问题 / 格式错误 | 检索到了，但生成得不对      | 优化Prompt、调整模型参数、加后处理 |

**实战数据（客服项目）**：

> 43条失败用例归因结果：
>
> - 72.1% 跟分类器误路由有关（L2层）
>
> - 其余分散在检索、生成、用例问题等
>
> ⇒ 最核心的问题是路由——把路由搞好了，大部分问题就解决了。

### 3.4 归因分析实操步骤

1. **捞失败用例**：把所有没通过的用例都捞出来
2. **设计分类体系**：先粗分几大类，后面再细化
3. **逐条标注**：给每条失败用例标上根因
4. **统计汇总**：各类根因的数量、占比，按数量排序
5. **找系统性问题**：哪类问题占比最高？那就是最该优先解决的
6. **钻进去细看**：占比最高的那类，具体都是什么情况？有没有规律？
7. **产出归因报告**：数据+结论+建议

**注意事项**：

- 标注的时候，如果遇到"不知道归哪类"的情况——说明你的分类体系有问题，需要调整

- 可以两个人独立标注，然后看一致率——一致率低，说明分类定义不清楚

- 归因是"分析"不是"甩锅"——重点是找到问题、解决问题，不是怪谁

### 3.5 相关性分析：找杠杆维度

除了"哪类问题最多"，你还要知道——**哪个维度的提升，对整体效果的拉动最大？**

**怎么做**：算各个维度跟总通过率的相关性系数。

| 维度    | 与通过率的相关性 | 杠杆等级     |
| ----- | -------- | -------- |
| 信息完整性 | 0.859    | ⭐⭐⭐⭐⭐ 最高 |
| 路由准确率 | 0.82     | ⭐⭐⭐⭐ 高   |
| 意图准确率 | 0.75     | ⭐⭐⭐ 中    |
| 幻觉率   | 0.6      | ⭐⭐ 低     |

**解读**：

- 信息完整性跟通过率相关性最高——说明提升信息完整性，对整体通过率的拉动最大

- 这就是**杠杆维度**——投入同样的精力，优化这个维度，收益最大

- 反过来，幻觉率相关性低——说明幻觉虽然不好，但对整体通过率的影响没那么大

**为什么要做这个分析？**

- 资源有限，你不可能什么都优化

- 找杠杆维度，就是找"投入产出比最高"的优化方向

- 把80%的精力，投入到20%收益最高的地方

## 四、第三步：优先级排序

### 4.1 优先级矩阵：影响面 × 修复难度

不是所有问题都要立刻修。怎么排优先级？

用**影响面 × 修复难度**的四象限矩阵：

```
          修复难度
    低 ←────────────→ 高
  ┌─────────┬─────────┐
高│  P0立即做 │  P2规划做 │
  │  影响大  │  影响大  │
影│  成本低  │  成本高  │
响├─────────┼─────────┤
面│  P1顺手做 │  P3再说  │
低│  影响小  │  影响小  │
  │  成本低  │  成本高  │
  └─────────┴─────────┘
```

| 象限        | 优先级    | 怎么做          |
| --------- | ------ | ------------ |
| 影响大 × 成本低 | **P0** | 立刻做，投入产出比最高  |
| 影响小 × 成本低 | **P1** | 顺手做，反正成本不高   |
| 影响大 × 成本高 | **P2** | 规划一下，找合适的时机做 |
| 影响小 × 成本高 | **P3** | 算了，不值得做      |

### 4.2 "影响面"怎么估？

影响面不是拍脑袋的，要有依据：

| 方法       | 说明                | 准确度   |
| -------- | ----------------- | ----- |
| **失败占比** | 这类失败占总失败的百分比      | 高     |
| **用户影响** | 影响多少用户/多少使用场景     | 中     |
| **严重程度** | 出了这个问题，后果有多严重     | 中（主观） |
| **业务价值** | 修复了之后，对业务指标的提升有多大 | 中     |

**实战案例**：

> 客服项目的优先级排序：
>
> - P0：优化分类器路由 —— 72.1%失败跟这个有关，影响面最大
>
> - P1：优化Prompt减少幻觉 —— 占比不高但成本低，顺手做
>
> - P2：补充知识库内容 —— 影响面大，但需要大量内容运营工作，成本高
>
> - P3：优化边缘场景的表述 —— 影响小，而且改起来工作量不小

### 4.3 优先级不是一成不变的

优先级会随着时间变化：

- 修了P0的问题之后，原来P1的可能变成P0了

- 业务重点变了，优先级也要跟着变

- 发现了新的严重问题，要插进来

**所以——定期（比如每周/每个迭代）重排一次优先级。**

### 4.4 一个常见误区："哪个最差先修哪个"

很多人会说："边界混淆通过率最低，只有 63.6%，先修这个！"

**这是错的。**

为什么？

- 边界混淆通过率是最低，但它只有22条用例——就算全修好了，整体通过率也提升不了多少

- 投诉分支通过率 85.1%（V2 复评基线，47 条用例；V1 基线为 78.7%，V3 修复后 100%），看起来比 63.6% 高，而且修复成本很低（只是改 Prompt）

- 算一下投入产出比——投诉分支的优化性价比更高

**核心原则**：

> **不是看"哪里最差"，是看"修哪里收益最大"。**
>
> 最差的地方，如果影响面很小，修了也没什么用。
> 看起来不是最差的地方，如果影响面大、修复成本低，反而应该先修。

## 五、第四步：优化实施

### 5.1 一次只解决一类问题

做优化的时候，**一次只改一个变量**——这是科学实验的基本原则。

为什么？

- 如果你一次改了五样东西，效果变好了——你不知道是哪一样起的作用

- 如果效果变差了——你也不知道是哪一样搞坏的

- 结果就是——你什么都没学到，下次还是不知道怎么做

**正确做法**：

- 一个迭代周期，集中解决一类问题

- 改完之后，跑评测看效果

- 有效 → 记录下来，知道这个方法管用

- 无效 → 分析为什么，换个方向

### 5.2 小步快跑，快速迭代

不要等"攒够了"再优化——小步快跑，每次改一点，每次验证一点。

**小步快跑的好处**：

1. **反馈快**——改完马上就知道效果，不用等很久
2. **风险小**——就算改坏了，也只是小问题，容易回滚
3. **学得快**——每一次迭代都能学到东西，积累经验
4. **节奏好**——有规律的迭代节奏，团队有奔头

**多大算"小步"？**

- 一个迭代周期（1-2周）能做完并验证的量

- 大概是1-3个优化项，不要太多

### 5.3 任务卡体系：让迭代可管理

这是从Vibe Coding实践中总结的方法——把每个迭代单元做成一张"任务卡"。

**一张任务卡包含**：

- 目标：做什么

- 背景：为什么做

- 涉及范围：改哪些文件、影响哪些功能

- 验收标准：怎么算做完了、怎么验证效果

- 优先级：P0/P1/P2/P3

**为什么要任务卡？**

1. **边界清晰**——一张卡只做一件事，做完就完
2. **可验证**——每张卡都有明确的验收标准
3. **可追踪**——做了什么、没做什么，一目了然
4. **可复用**——类似的任务，直接套用之前的卡

**实战案例**：

> 穿搭项目有31张任务卡，从Phase 0到Phase 15+。
> 每张卡一个迭代单元，一卡一commit，做完就验收。
> 31张卡做完，产品从0到1完整跑起来了。

## 六、第五步：效果验证

### 6.1 验证的三种方法

| 方法        | 适用场景        | 可信度    | 成本 |
| --------- | ----------- | ------ | -- |
| **前后对比**  | 优化前后用同一套评测测 | 中      | 低  |
| **A/B测试** | 有真实用户的产品    | 高      | 中  |
| **黄金集回归** | 每次改动必做，防回归  | 高（防回归） | 低  |

### 6.2 前后对比：注意"评测污染"

**怎么做**：

- 优化前：跑一遍评测，记录数据

- 优化后：再跑一遍评测，对比数据

**有个坑：评测工具本身可能变了**

- 如果你优化了Judge的Prompt，那评测标准就变了

- 这时候优化前后的分数就不可比了——你不知道是产品变好了，还是Judge变松了

**怎么解决？——复评基准**

- 用优化后的Judge，对优化前的版本重新跑一遍

- 这样两个版本用的是同一套评测标准，结果才可比

**这是个大坑，很多团队都踩过**——越优化分数越高，但用户反馈没变好。其实就是评测标准在偷偷变松。

### 6.3 A/B测试：黄金标准

如果你有真实用户，A/B测试是验证效果的黄金标准。

**基本原理**：

- 把用户随机分成两组：A组（对照组，旧版本）、B组（实验组，新版本）

- 两组用户同时用

- 对比两组的核心指标——如果B组显著更好，说明优化有效

**为什么要随机分组？**

- 确保两组用户的构成是一样的

- 这样才能排除其他因素的干扰，确定"是版本差异导致了指标差异"

**统计显著性**：

- 不是B组比A组高一点就叫"更好"

- 要做统计检验，确保差异不是随机波动导致的

- 常用的检验方法：McNemar检验（配对数据）、t检验、卡方检验

**实战案例（客服项目）**：

> 优化后通过率从91.5%提升到97.0%。
> 普通z检验p=0.56，会误判为不显著——但McNemar精确检验（聚焦不一致对）p=0.02，证明提升统计显著。
>
> 同时检测到2条回归用例——优化了大部分，但搞坏了两个小地方，需要修。

### 6.4 黄金集回归：防回归的底线

黄金集回归不是用来验证"有没有变好"的，是用来验证"有没有变坏"的。

**每次改代码、每次发布，都要跑一遍黄金集。**

- 全绿 → 放心，没搞坏旧功能

- 红了 → 糟糕，有回归，赶紧修

**三层质量门禁**：

```
代码提交 → Gate1（10-30条，快速）→ 日常开发，每次必跑
              ↓
           Gate2（50-100条，标准）→ 版本合并前跑
              ↓
           Gate3（全量，全面）→ 正式发布前跑
```

**为什么要分层？**

- 全量跑一次很贵、很慢——不能每次都跑

- 但每次都不跑，又怕搞坏了东西

- 分层就是平衡——小改动跑Gate1，重要改动跑Gate2，发布前跑Gate3

### 6.5 怎么判断优化"真的有效"？

不是看分数涨了就叫有效。你还要排除这些可能性：

| 假象      | 怎么排除                 |
| ------- | -------------------- |
| 评测标准变了  | 用同一套评测基准复评（复评基准方法）   |
| 随机波动    | 做统计显著性检验，p值<0.05才算显著 |
| 样本量太小   | 确保有足够的用例/用户，统计功效够    |
| 其他变量干扰  | A/B测试要随机分组，控制其他变量    |
| 只在测试集上好 | 看线上真实数据有没有对应提升       |

**核心原则**：

> **对优化结果保持怀疑。**
>
> 分数涨了，先别急着庆祝——先想想，有没有可能是假的？
> 排除了所有假象之后，再确认是真的提升了。

## 七、迭代节奏：小步快跑，持续改进

### 7.1 一个标准迭代周期

| 阶段     | 做什么          | 时间占比 |
| ------ | ------------ | ---- |
| **分析** | 看数据、做归因、排优先级 | 20%  |
| **实施** | 做优化、改代码      | 40%  |
| **验证** | 跑评测、看效果、修回归  | 30%  |
| **复盘** | 总结经验、更新方法论文档 | 10%  |

**很多团队的问题**：全在"实施"，分析和验证都不够。

- 结果就是——做了很多改动，但不知道哪些有用、哪些没用

- 看起来很忙，但产品没什么实质进步

### 7.2 迭代的"验证链"

这是从产品经验里总结的——从一个想法到最终决策，要经过6步验证：

```
直觉 → 术语对齐 → 代码对质 → 联网调研 → 低成本实验 → 数据拍板
```

| 步骤        | 做什么              | 目的          |
| --------- | ---------------- | ----------- |
| **直觉**    | 我觉得应该是这样         | 起点，不是终点     |
| **术语对齐**  | 先把词对准了，确保说的是一回事  | 避免鸡同鸭讲      |
| **代码对质**  | 去看代码，确认现状是怎样的    | 避免基于错误的假设讨论 |
| **联网调研**  | 看看别人怎么做的、有没有数据支撑 | 借别人的经验      |
| **低成本实验** | 花最小的代价验证一下       | 小成本试错       |
| **数据拍板**  | 看实验数据，做决策        | 用数据说话       |

**为什么要有这条链？**

- 很多产品决策，停留在"直觉"层面——我觉得、我认为、我感觉

- 但直觉经常是错的

- 每往前走一步，你对问题的理解就深一层

- 走到最后一步再拍板，决策质量会高很多

**实战案例**：

> "我觉得加了提示词之后变慢了"——这是直觉。
>
> 去查代码和数据——发现输入走并行prefill，影响很小，大头是输出decode的串行长度。
>
> ⇒ 直觉错了。如果不做代码对质，就在错误的方向上优化了。

### 7.3 复盘：让每次迭代都有沉淀

做完一个迭代，不要急着开始下一个——花点时间复盘。

**复盘回答四个问题**：

1. **哪里没做好？** —— 哪些地方偏离了计划？为什么？
2. **改了什么？** —— 实际做的跟计划有什么不一样？为什么改？
3. **方法有什么问题？** —— 任务卡写得对不对？验收标准合不合理？
4. **什么没做？** —— 哪些计划内的事情没做完？为什么？

**为什么复盘很重要？**

- 不复盘，踩过的坑下次还会踩

- 复盘了，经验才能沉淀下来，越做越好

- 好的团队和差的团队，差距就在这里——差的团队重复踩坑，好的团队每次都在进步

## 八、常见坑 & 避坑指南

### 坑1：只看总分，不拆维度

**症状**："通过率95%，挺好的。"——但不知道那5%是哪里错了。

**后果**：找不到优化方向，瞎试。

**避坑**：一定要拆维度、做归因。知道哪里错了，才能对症下药。

### 坑2：一次改太多，不知道什么有用

**症状**：一个版本改了十几样东西，然后数据变好了——但不知道是哪样起的作用。

**后果**：学不到东西，下次还是瞎试。

**避坑**：一次只改一个变量，每次验证一个假设。小步快跑，每次迭代都要有明确的结论。

### 坑3：评测工具自己在变，结果不可比

**症状**：越优化分数越高，但用户反馈没变好。

**后果**：自我感觉良好，但实际没进步。

**避坑**：用复评基准——同一套评测基准，对所有历史版本重跑。确保比较是公平的。

### 坑4：哪里最差先修哪里

**症状**："这个分支通过率最低，先修这个！"

**后果**：花了很多精力修一个影响面很小的问题，整体提升有限。

**避坑**：用"影响面×修复难度"矩阵排优先级。不是看哪里最差，是看修哪里收益最大。

### 坑5：只修问题，不加功能

**症状**："数据驱动嘛，就盯着Bad Case修。"

**后果**：产品越来越稳，但也越来越"平"——没有惊喜，没有增长。

**避坑**：数据驱动不是"只修问题"。修问题是基础（P0/P1），但也要留一部分精力做新功能探索（P2/P3）。两者要有平衡。

### 坑6：过度优化，边际收益递减

**症状**：从95%优化到96%花了一周，从96%到97%花了两周，从97%到98%花了一个月……

**后果**：投入越来越多，收益越来越小。性价比太低。

**避坑**：算一下投入产出比——当边际收益低于投入的时候，就该停了。把精力转到更有价值的地方去。

## 九、下一个项目复用检查清单

做下一个项目的时候，照着这个清单建立迭代机制：

### 迭代基础建设

- [ ] 有评测体系（没的话先建——参考评测体系方法论）

- [ ] 建立Bad Case收集渠道（评测/用户反馈/日志/内部使用）

- [ ] 设计失败分类体系（3-5类起步，迭代细化）

- [ ] 建Gate1黄金集（10-30条核心用例）

- [ ] 确定迭代周期（1周/2周/1个月）

### 每个迭代周期必做

- [ ] **分析阶段（20%时间）**
  - [ ] 跑最新评测数据

  - [ ] 做失败归因统计

  - [ ] 找杠杆维度（相关性分析）

  - [ ] 用优先级矩阵排P0/P1/P2

  - [ ] 选定本迭代要做的1-3件事

- [ ] **实施阶段（40%时间）**
  - [ ] 写任务卡（目标/背景/验收标准）

  - [ ] 一次只解决一类问题

  - [ ] 小步快跑，中间及时验证

- [ ] **验证阶段（30%时间）**
  - [ ] 跑前后对比评测

  - [ ] 跑黄金集回归（至少Gate1）

  - [ ] 检查有没有回归（新的失败用例）

  - [ ] 确认提升是真实的（排除评测污染/随机波动）

  - [ ] 记录结果（有效/无效/部分有效）

- [ ] **复盘阶段（10%时间）**
  - [ ] 回答四个问题：哪里没做好/改了什么/方法问题/什么没做

  - [ ] 沉淀经验（有用的方法、踩过的坑）

  - [ ] 更新方法论文档（如果有新发现）

### 长期建设

- [ ] 逐步扩充黄金集（Gate2、Gate3）

- [ ] 完善分类体系（从粗到细）

- [ ] 建立A/B测试能力（等有真实用户之后）

- [ ] 搭建数据看板（可视化核心指标变化）

## 最后一句话

**数据驱动不是让数据替你做决策，而是让数据帮你做更好的决策。**

数据不会告诉你该做什么——那是产品经理的判断。
但数据会告诉你——你做的对不对、效果好不好、哪里需要改。

用好数据，你就能比别人少踩坑、少走弯路、迭代得更快。
