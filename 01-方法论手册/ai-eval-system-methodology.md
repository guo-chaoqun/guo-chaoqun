# AI产品评测体系搭建方法论 · 操作手册

> 生成日期：2026.10.06
> 来源：电商客服RAG评测项目 + AI穿搭导购项目（97份文档提炼）
> 定位：可复用的操作手册——下一个AI项目直接照着做，不用从零开始

***

## 为什么需要评测体系？

> **没有评测，就没有迭代。**

传统软件是"写代码→测试→上线"，功能是确定的——要么对，要么错。

AI产品不一样——输出是概率性的，没有绝对的"对"和"错"。你怎么知道这个版本比上个版本好？你怎么知道优化是真的有用，还是你感觉变好？

**没有评测体系的AI产品，就是在裸奔。**

***

## 一、评测体系全景图

### 1.1 三层评测模型

任何AI产品的评测，都要分三层来看：

```
┌─────────────────────────────────────────┐
│           商业层（Business）            │
│  成本节约 / 转化率提升 / 留存变化 / ROI  │
├─────────────────────────────────────────┤
│           产品层（Product）             │
│  任务完成率 / 用户满意度 / 交互轮次     │
│  拒绝率 / 转人工率 / 首解率             │
├─────────────────────────────────────────┤
│           模型层（Model）               │
│  准确率 / 召回率 / 幻觉率 / 延迟       │
│  Token消耗 / 要点覆盖率 / 违规率       │
└─────────────────────────────────────────┘
```

| 层级  | 给谁看    | 核心问题              |
| --- | ------ | ----------------- |
| 模型层 | 产品+算法  | 模型本身效果怎么样？哪里好哪里差？ |
| 产品层 | 产品+用户  | 用户用起来爽不爽？任务能不能完成？ |
| 商业层 | 老板+投资人 | 花的钱值不值？ROI是多少？    |

**新手常见误区**：只看模型层，不看产品层和商业层。

- 模型准确率从90%提到95%，但用户满意度没涨——为什么？

- 因为模型提升的那5%，用户根本感知不到。

- 或者模型是变准了，但回复变长了，用户等不及走了。

**正确的做法**：三层都看，但不同阶段重点不同。

- 早期（MVP阶段）：重点看模型层——先把基础效果做对

- 中期（用户测试）：重点看产品层——用户用起来怎么样

- 后期（商业化）：重点看商业层——到底值不值钱

***

| # | 模块          | 做什么                  | 优先级   |

## 二、评测维度设计

### 2.1 怎么选评测维度？

**核心原则**：维度要跟产品价值挂钩，不是越多越好。

**设计步骤**：

1. 先想：用户为什么用这个产品？——核心价值是什么？
2. 再想：什么情况下产品是"好用的"？——拆解成具体维度
3. 最后想：每个维度怎么衡量？——定义评分标准

**反例**：随便列一堆维度，看起来很全面，但每个维度都跟核心价值没关系。

***

### 2.2 案例：电商客服RAG的7维度设计

| # | 维度    | 定义               | 为什么选这个维度？                  |
| - | ----- | ---------------- | -------------------------- |
| 1 | 意图准确率 | 用户说的话，有没有听懂他要干嘛  | 听不懂就全错了，这是第一道门             |
| 2 | 分支路由  | 有没有进对业务窗口（6 路分类） | 分错了分支，知识库都不对，回答肯定错         |
| 3 | 答案相关性 | 回答是否切题、聚焦问题      | 不切题=答非所问                   |
| 4 | 信息完整性 | 该说的点都说了吗         | 答了但没答全，等于没答对（本项目最弱维度，是杠杆点） |
| 5 | 忠实度   | 有没有编造知识库中没有的信息   | 胡说八道比不回答更糟——丧失用户信任         |
| 6 | 语气合规  | 客服语气对不对、是否得体     | 语气影响信任感                    |
| 7 | 边界正确性 | 边界场景处理对不对、守住权限   | 合规红线，绝对不能碰                 |

**这 7 个维度的逻辑关系**：

```
意图准确 → 分支路由 → 答案相关 → 信息完整 → 忠实（不瞎编）→ 语气合规 → 边界兜底
  （听懂）   （走对路）   （答到"点"） （说全了）    （不编造）     （得体）     （守边界）
```

是一个漏斗——前面的错了，后面全白搭。

***

### 2.3 案例：AI穿搭的评测维度探索

穿搭项目尝试过做"设计维度自动评判"（廓形/层次/身形/风格/组合五维评分），但**失败了**。

**失败原因**：

1. **位置偏置**：Judge有87.5%的概率选"左边"的选项——不是看内容，是看位置
2. **分辨力不足**：两套方案的分数差在1分以内（满分50）——分不出胜负
3. **量表违规**：模型经常打出超出1-5分范围的分数

**重要教训**：

> **不是所有维度都适合用LLM Judge来评。**
>
> 客观维度（对不对、全不全、有没有违规）——LLM Judge能评
> 主观维度（好不好看、风格怎么样、设计优不优）——LLM Judge评不准，至少当前模型不行

**怎么办？**

- 主观维度：用人工盲评

- 客观维度：用LLM Judge自动化

- 不要强求"全自动化"——该人评的就人评

***

### 2.4 维度设计的3个避坑指南

#### 坑1：维度之间强相关，等于重复测

**例子**：如果你同时测"回答准确率"和"要点覆盖率"——这两个高度相关，测一个就够了。

**怎么避免**：做完评测之后，跑一下相关性分析。如果两个维度的相关系数 > 0.8，说明高度重合，可以考虑合并。

***

#### 坑2：维度太粗，不知道问题出在哪

**反例**：只测一个"整体满意度"——满意度低了，但你不知道是回答不准、还是太慢、还是语气不好。

**正确做法**：拆成足够细的维度——细到能定位问题。

***

#### 坑3：维度太多，评测成本爆炸

**反例**：一口气搞20个维度——每条用例都要评20个维度，成本直接翻20倍。

**正确做法**：

- 核心维度（3-5个）：每条用例都评

- 扩展维度（5-10个）：抽样评，只在专项分析时用

***

## 三、评测用例设计

### 3.1 用例设计的核心原则

> **评测用例要覆盖真实用户会遇到的所有场景，而且要分层分级。**

不是随便找100条问题测一下就行——你要知道：

- 哪些是高频场景？（占比大，优先保证）

- 哪些是边界场景？（容易错，重点关注）

- 哪些是对抗场景？（用户故意刁难，要防住）

- 哪些是违禁场景？（合规红线，绝对不能错）

***

### 3.2 用例的5种类型

| 类型   | 说明        | 占比建议   | 目的      |
| ---- | --------- | ------ | ------- |
| 单轮正常 | 正常的单轮问答   | 50-60% | 基础能力保底  |
| 多轮对话 | 有上下文的多轮交互 | 15-20% | 上下文理解能力 |
| 边界场景 | 模糊的、容易混淆的 | 10-15% | 发现系统薄弱点 |
| 对抗测试 | 故意刁难、诱导犯错 | 5-10%  | 鲁棒性测试   |
| 违禁测试 | 不该回答的问题   | 5-10%  | 合规红线测试  |

***

### 3.3 用例的难度分级

| 难度 | 说明             | 占比建议 |
| -- | -------------- | ---- |
| 简单 | 知识库中有明确答案的常见问题 | 60%  |
| 中等 | 需要一定推理或综合多段内容  | 30%  |
| 困难 | 边界模糊、需要深度理解    | 10%  |

**为什么要分级？**

- 如果全是简单题——通过率99%，但你不知道系统真实水平

- 如果全是难题——通过率30%，也说明不了什么

- 合理的难度分布，才能反映系统的真实能力

***

### 3.4 用例设计的实操步骤

1. **梳理业务场景**：把产品的所有使用场景列出来
2. **按类型和难度分类**：每种类型、每个难度大概占多少
3. **编写用例**：每条用例包含——输入、预期输出、评分标准、所属分类
4. **审核用例**：另一个人审核，确保用例质量
5. **小规模试测**：先测20-30条，看看用例有没有问题
6. **完善调整**：根据试测结果调整用例

***

### 3.5 用例数量多少合适？

没有标准答案，给你一个参考：

| 产品阶段  | 用例数量     | 目的         |
| ----- | -------- | ---------- |
| MVP验证 | 50-100条  | 快速验证方向对不对  |
| 正式上线前 | 300-500条 | 全面评估，保证质量  |
| 成熟产品  | 1000+条   | 持续迭代，精细化优化 |

**关键不是数量，是覆盖度**——1000条重复的简单题，不如300条覆盖全面的好用例。

## 四、评测执行方式：规则 + LLM Judge + 人工

### 4.1 三种评测方式的对比

| 方式        | 优点         | 缺点        | 适用场景              |
| --------- | ---------- | --------- | ----------------- |
| 规则评测      | 快、准、零成本    | 只能测确定性的东西 | 分类、格式、关键词匹配       |
| LLM Judge | 快、成本低、可自动化 | 不一定准、有偏置  | 内容质量、要点覆盖、幻觉检测    |
| 人工评测      | 最准、最靠谱     | 慢、贵、不可控   | 主观质量、最终验证、Judge校准 |

**最佳实践：双通道/三通道混合**

- 第一层：规则预检——能规则判的，直接判，零成本

- 第二层：LLM Judge——复杂的、需要理解的，让大模型评

- 第三层：人工抽检——抽样验证Judge的准确性，做最终把关

***

### 4.2 规则评测：哪些可以用规则？

| 可规则化的   | 怎么做           |
| ------- | ------------- |
| 分类对不对   | 跟预期分类比对       |
| 格式对不对   | JSON Schema校验 |
| 有没有违禁词  | 关键词匹配         |
| 要点有没有覆盖 | 关键词匹配 + 正则    |
| 有没有引用来源 | 检查引用标记        |
| 长度是否合规  | 字符数/Token数    |

**原则：能规则化的，坚决不用大模型评。**

- 规则 = 100%准确 + 零成本 + 瞬间出结果

- 大模型 = 可能不准 + 花钱 + 慢

***

### 4.3 人工评测：哪些指标必须人来判？（2026-10-14 补充）

> 素材来源：AI穿搭项目《穿搭审美评分SOP-v1.0》第 7 节"自动裁判的定位"。

**不要用"主观/客观"来粗分。** "这个维度很主观所以人工评"是经不起追问的——主观在哪？为什么模型评不了？真正可用的是下面两条判据。

#### 判据一：评判标准能不能写成可观察的规则

- 能写成"出现 X 就判 Y"的（出现违禁词→违规、JSON 字段缺失→格式错）→ 规则层
- 能用文字把各档位锚点写清楚的（要点覆盖、相关性、幻觉）→ LLM Judge
- 怎么写都只能落到"你懂的那种好""说不上来但就是不对"→ 人工

#### 判据二：自动分跟人工金标准的相关性达不达标

即使模型能吐出一个分数，也不能直接采信。**所有自动分必须与人工 MOS（平均主观意见分）计算 Spearman 等级相关，不达标不采信。** 模型在某个维度上跟人评对齐了，才允许它在这个维度上替代人；没对齐，它永远只是"建议分"。

#### 必须人评的指标，通常有三个特征

1. **依赖整体感受，而不是单个特征**：判断对象是多个元素之间的"关系"，不是元素本身（单个颜色能取色读出 RGB，颜色搭在一起"显不显脏"读不出来）。
2. **没有唯一正确答案，且随人群漂移**：不同客群、季节、潮流下标准不一样，需要定期复核重标定。
3. **必须结合题面前提做相对判断**：同一个方案，对梨形身材是扬长避短，对苹果形可能就是反向——脱离用户档案无法评分。

#### 穿搭项目的实证：指标按"判罚权"分三层

| 类型 | 穿搭项目里的具体指标 | 判罚权归属 |
| --- | --- | --- |
| 硬属性 | 颜色、件数、长度、露肤、温度 | 规则层/VLM 自动判，仍按比例抽检 |
| 半客观 | 合身度、层次、场合适当性 | 模型给建议分，人工抽检校准 |
| 纯审美 | 色彩感受、风格纯度、组合美感 | **人工 MOS 金标准终审**，模型最多初筛 |

#### 四个"抽象到只能人评"的具体例子（出自穿搭七维 SOP）

1. **风格统一度——"像不像韩系"**：方案里带"韩系"两个字不加分，要看整体视觉语言。VLM 本质是关键词生物，看到奶油色、低饱和就报"韩系"，但判不出一双金属铆钉靴混进来之后整套语言已经崩了。SOP 明确规定：判不准标 dispute，不靠关键词命中给分。
2. **色彩和谐——"显脏"**：颜色是硬属性，取色就能读出来；但 1 分锚点写的是"上下装明度/彩度严重割裂显脏"。"脏"不是任何一个颜色的属性，是多个颜色之间的关系感受——机器能取色，判不了关系。
3. **组合逻辑——"整套像一起买的"**：5 分要求每件单品都能说清"为什么在这"，1 分是"三件分别属于三个世界"。这是目的层判断（理解单品存在的意图），不是视觉特征匹配。
4. **身形扬长避短——"看不出刻意遮"**："有没有高腰"可以机检（半客观），但 5 分要求多处协同且自然、看不出刻意——自不自然是审美，人眼一秒感觉到，规则写不出来。

#### 为什么不让模型终审：本项目的实测证据

不是"我觉得 AI 评不准审美"，而是做过实验证伪（2026-09 design-judge 实验）：

- 双序交换评同一对方案，**8 次里 7 次选位置在左的，位置偏置 87.5%**
- 违反 1-5 分量表，**打出 8 分、9 分**
- 4 对方案里 3 对总分差 ≤ 1（满分 50），**没有分辨力**，两版 rubric 均未过校准门禁
- 行业旁证：Gemini 2.0 Flash 服饰细粒度属性 macro F1 约 56.8%、GPT-4o mini 约 43.3%；微调 Florence-2 风格识别 F1 约 0.75——硬属性勉强可用，风格审美远不能当裁判

#### 落地时的两条诚实口径

- **人评自身也要过一致性门禁**：2 人用 Cohen's Kappa、3 人及以上用 Fleiss' Kappa，≥0.80 标准可用、≥0.85 才放量；不达标就改标准（补锚点/正反例），不是改评分人。
- **单人模式不能冒充多人一致性**：只有一个人时隔 3 天盲评两轮，只能报告"自一致性"，对外作品集必须明确标注，不得谎称标注员间一致性。

## 五、LLM Judge 设计方法论

### 5.1 什么是好的LLM Judge？

一个好的LLM Judge，要满足三个条件：

1. **准确**：跟人的判断一致率高
2. **稳定**：同一条用例测多次，结果差不多
3. **无偏**：不会因为位置、顺序、措辞等因素影响判断

***

### 5.2 Judge Prompt 的标准结构

```
1. 角色设定
   你是一个XX评测专家，负责……

2. 评测任务
   你需要根据以下标准，对XX进行评测……

3. 评分Rubric（核心！）
   维度1：XX
     1分：……
     3分：……
     5分：……
   维度2：XX
     ……

4. 输出格式
   严格按照以下JSON格式输出：
   {
     "score": {
       "dim1": n,
       "dim2": n
     },
     "reason": "一句话理由"
   }

5. 注意事项
   - 不要受XX影响
   - 严格按照评分标准打分
   - ……
```

***

### 5.3 Rubric（评分标准）怎么写？

Rubric是Judge的灵魂——Rubric写得不好，Judge再强也没用。

**好的Rubric的特点**：

1. **有明确的评分锚点**——不是笼统的"好/中/差"，而是具体描述1分、3分、5分分别是什么样
2. **可操作**——评判者看完就知道怎么打，不需要猜
3. **维度独立**——每个维度评不同的东西，不要重叠

**例子（要点覆盖率）**：

- 5分：所有要点都覆盖到了，而且-\*/表述准确

- 4分：覆盖了大部分要点，只有1个次要要点遗漏

- 3分：覆盖了核心要点，但有2-3个要点遗漏

- 2分：只覆盖了少部分要点，大部分没说到

- 1分：完全没答到点子上

> **完整版见《Rubric 设计方法论》**（`01-方法论手册/rubric-design-methodology.md`）：含 Rubric 四属性定义与边界、四部件解剖、六条设计原则、四种判分形式选型、**6 个完整实例**（客服完整性/幻觉二分/意图行为特征/穿搭 Gate+七维/Agent 轨迹 think-tool_call-final_response/SFT 数据四维）、反面教材表与写完自检 8 问。本节是它的简版。

### 5.4 Judge 类实验的三项探针（重要！）

这是从实践中踩坑踩出来的——做Judge实验，必须自带这三项验证，否则你可能得出完全错误的结论。

#### 探针1：位置偏置检测

**问题**：LLM Judge有选择"左边"或"第一个"的倾向——不是看内容，是看位置。

**怎么检测**：做双序交换——同一对内容，正着放一次，反着放一次。如果两次结果不一致，说明有位置偏置。

**我们的实战数据**：

- v1版本：8次调用7次选"左"，偏置率87.5%

- v2版本：优化后降到75%，但仍然存在

**怎么缓解**：

- 让Judge给两边分别打分，而不是直接选"哪个好"

- 双序结果取平均，抵消位置影响

- 但这只是缓解，不能根治——主观维度的Judge，位置偏置是普遍问题

***

#### 探针2：量表遵从性检测

**问题**：你定义的是1-5分，但模型可能打出8分、9分——根本不按你的量表来。

**怎么检测**：检查输出的分数是否在定义的范围内。

**我们的实战数据**：

- 4对测试中有2对打出了8-9分（量表是1-5）

- 这两对的"命中"其实是无效的，因为分数和不可比

**怎么缓解**：

- 在Prompt里反复强调分数范围

- 加后处理校验——超出范围的结果打回重试

- 但根本上，这是模型能力的问题

***

#### 探针3：裕度分布分析

**问题**：如果两个选项的分数差只有0.5分（满分50），你怎么知道是真的有差异，还是噪声？

**怎么看**：统计所有用例的分数差分布。

- 如果大部分用例的分差都很小（<2分），说明Judge分辨力不够

- 如果分差分布比较分散，说明Judge能分出好坏

**我们的实战数据**：

- 4对中有3对的总分差 ≤ 1分（满分50）

- 说明Judge对设计维度基本没有分辨力——分不出好坏

***

### 5.5 什么时候用LLM Judge，什么时候不用？

✅ **适合用Judge的**：

- 要点覆盖率（有没有说到关键点）

- 幻觉检测（有没有编造信息）

- 相关性判断（回答跟问题对不对得上）

- 语气/风格检测（是不是符合人设）

- 信息完整性（有没有遗漏重要信息）

❌ **不适合用Judge的（当前模型能力）**：

- 审美判断（好不好看、设计优不优）

- 创意评估（有没有创意、够不够新颖）

- 复杂的逻辑推理正确性

- 需要深度领域专业知识的判断

**核心判断标准**：**你能不能用文字写清楚评判标准？**

- 能写清楚 → 大概率可以用Judge

- 写不清楚，只能"你懂的" → 别用Judge，用人评（"哪些指标必须人评、怎么分层判罚权、穿搭项目的具体实证"见 4.3）

## 六、黄金集与回归测试

### 6.1 什么是黄金集？

黄金集（Golden Set）就是一套**固定的、经过验证的测试用例**——每次改完代码，都用这套用例跑一遍，看看有没有把旧功能搞坏。

**为什么叫"黄金"？**

- 因为它是你质量保障的"硬通货"——有了它，你改代码就有底气

- 不是随便选的，是精心挑选的，覆盖了核心功能和常见问题

***

### 6.2 黄金集怎么建？

1. **从评测用例中选**：挑最核心、最有代表性的用例
2. **覆盖核心路径**：每个主要功能、每个主要分支都要有
3. **包含历史Bad Case**：之前出过问题的，一定要加进去——防止重犯
4. **控制规模**：不是越大越好——太大了跑起来慢，成本高

   - 小型黄金集（Gate1）：10-30条 —— 快速检测，每次提交必跑

   - 中型黄金集（Gate2）：50-100条 —— 版本发布前跑

   - 大型黄金集（Gate3）：全量用例 —— 重大版本前跑

***

### 6.3 三层质量门禁

```
代码提交 → Gate1（快速，10-30条）→ 开发日常必跑
              ↓ 通过
           Gate2（标准，50-100条）→ 版本合并前跑
              ↓ 通过
           Gate3（全量，500条+）→ 正式发布前跑
```

**Gate1**：快速检测，几分钟跑完，每次提交都跑——有问题立刻发现
**Gate2**：标准检测，几十分钟，版本合并前跑——确保没有大的回归
**Gate3**：全量检测，几小时，正式发布前跑——全面保障质量

***

### 6.4 复评基准方法（解决评测污染问题）

#### 什么是评测污染？

你优化了Judge的Prompt，然后用新Judge去测新版本，发现分数提升了——但你不知道是系统真的变好了，还是Judge变松了。

这就是**评测污染**——评测工具本身变了，导致不同版本的结果不可比。

#### 怎么解决？——复评基准

用**同一版本的Judge**，对**所有历史版本**重新跑一遍评测。

```
时间线：
  V1版本 → 用Judge v1评测 → 分数 85分
  V2版本 → 用Judge v2评测 → 分数 90分  ❌ 不可比！

复评后：
  V1版本 → 用Judge v2重评 → 分数 87分
  V2版本 → 用Judge v2评测 → 分数 90分  ✅ 可比！
  真实提升：3分，不是5分
```

**为什么重要？**

- 如果没有复评基准，你可能以为自己进步了，其实只是评测标准变松了

- 很多团队都踩过这个坑——越优化分数越高，用户反馈却没变好

***

## 七、失败归因分析

### 7.1 为什么要做归因？

知道"通过率是多少"还不够，你还要知道"为什么没通过"。

- 通过率80%——那20%是为什么错的？

- 是检索的问题？还是生成的问题？还是Prompt的问题？

- 不同的原因，优化方向完全不一样

**没有归因的评测，就像看病只测体温，不做检查——知道你发烧了，但不知道为什么发烧。**

***

### 7.2 RAG系统的三层失败模型

```
用户提问 → 检索 → 上下文组装 → 生成 → 回答
            ↓         ↓          ↓
         L1失败    L2失败     L3失败
         （没找到）  （找错了）  （不会说）
```

| 层级      | 失败类型        | 表现         | 优化方向            |
| ------- | ----------- | ---------- | --------------- |
| L1 检索层  | 检索失败        | 知识库中没有相关内容 | 补充知识库、优化切片      |
| L2 上下文层 | 路由错误 / 检索不准 | 找到了但找错了    | 优化检索策略、优化路由     |
| L3 生成层  | 幻觉 / 表述问题   | 找对了但说不对    | 优化Prompt、优化模型参数 |

***

### 7.3 归因分析实操步骤

1. **收集失败用例**：把所有没通过的用例捞出来
2. **设计分类体系**：先定好有哪几类根因（可以从3-5类开始，迭代细化）
3. **逐条标注**：给每条失败用例标上根因
4. **统计汇总**：各类根因的数量、占比
5. **找系统性问题**：哪类根因占比最高？就是最该优先解决的
6. **排优先级**：影响面 × 修复难度 = 优先级

**实战案例（客服项目）**：

- 43条失败用例，做了8类根因分类

- 发现**72.1%的失败跟分类器误路由有关**——这就是最高优先级的问题

- 针对性优化后，边界混淆场景准确率从63.6%提升到77.3%

***

### 7.4 相关性分析：找杠杆维度

除了归因，还要看——**哪个维度的提升，对整体通过率的拉动最大？**

做法：算各个维度跟通过率的相关性系数。

**实战案例**：

- 信息完整性与通过率的相关性 r = 0.859——最高

- 说明：提升信息完整性，对整体通过率的拉动最大

- 这就是**杠杆维度**——投入同样的精力，优化这个维度收益最大

***

### 7.5 优先级矩阵：先修什么？

不是所有问题都要立刻修。怎么排优先级？

用**影响面 × 修复难度**矩阵：

```
          修复难度
    低 ←────────────→ 高
  ┌─────────┬─────────┐
高│  P0优先  │  P2考虑  │
  │  影响大  │  影响大  │
影│  成本低  │  成本高  │
响├─────────┼─────────┤
面│  P1再看  │  P3再说  │
低│  影响小  │  影响小  │
  │  成本低  │  成本高  │
  └─────────┴─────────┘
```

- **P0**：影响大、成本低 —— 立刻做，投入产出比最高

- **P1**：影响小、成本低 —— 顺手做

- **P2**：影响大、成本高 —— 规划一下，找合适的时机做

- **P3**：影响小、成本高 —— 算了，不值得做

***

## 八、盲评与人工验证

### 8.1 为什么要盲评？

人评测有个大问题——**主观偏见**。

- 你知道哪个是新版本，哪个是旧版本——你会倾向于觉得新版本好

- 你知道哪个是A方案，哪个是B方案——你会倾向于你喜欢的那个方案

**怎么消除？——盲评。**

把标识去掉，只看内容，你不知道哪个是哪个，凭真实感受来判。

***

### 8.2 盲评怎么做？

1. **准备材料**：把要对比的两个版本的输出，混在一起
2. **匿名化**：去掉所有能区分版本的标识，只标"左/右"或"A/B"
3. **随机顺序**：每组的左右顺序随机，避免位置偏置
4. **评判**：只看内容，判"左好/右好/平"
5. **揭盲**：判完之后，再看左右分别对应哪个版本
6. **统计**：计算新版本被判优的比例

**通过标准怎么定？**

- 比如6组对比，改后被判优 ≥5/6 才算过

- 为什么不是6/6？——允许有1组平局或误判，但必须绝大多数更好

***

### 8.3 盲评的注意事项

1. **样本量不能太少**：3组以下没有统计意义，至少5-6组起步
2. **要控制变量**：确保你测的是你想测的那个变量，其他都不变
3. **评判标准要提前定**：判之前先说清楚——什么算"好"？是更准确？还是更通顺？还是更专业？
4. **可以多人评**：多个人盲评，取一致率——更客观

***

## 九、变异测试：验证评测体系本身

### 9.1 什么是变异测试？

你写了100条断言，你怎么知道这些断言是有用的？——会不会代码全错了，断言还全绿？

**变异测试**就是验证"测试能不能测出bug"的方法：

1. 故意在代码里植入错误（"变异"）
2. 跑测试
3. 如果测试能测出这个错误（变红），说明测试有效
4. 如果测试没测出来（还是绿的），说明测试有漏洞

**变异测试通过率 = 能测出的变异数 / 总变异数**

通过率越高，说明你的测试越靠谱。

***

### 9.2 为什么要做变异测试？

很多团队的测试看起来覆盖率很高——90%、95%——但实际上很多测试是"凑数"的，根本测不出问题。

变异测试就是给你的测试做一次体检——看看你的测试是真的有用，还是只是看起来好看。

***

### 9.3 实战案例：断言的可证伪性

穿搭项目做了变异测试——60+把"变异刀"，故意在代码的各个地方植入错误，看断言能不能测出来。

**发现了什么？**

- 有些断言是"永真"的——不管代码怎么错，它都是绿的

- 有些断言太松了——小错误测不出来

- 然后针对性地加强了这些薄弱的地方

**结论**：

> **"判据能不能证伪"是最该先做的事。**
>
> 不能证伪的断言，写了等于没写——只是给自己心理安慰而已。

***

## 十、从零搭建评测体系的9步流程

> 拿到一个新的AI产品，怎么从0到1搭评测体系？按这个步骤来。

### Step 1：明确评测目标

- 为什么要做评测？——找问题？验效果？做对比？

- 给谁看？——自己？团队？老板？

- 不同的目标，评测的重点不一样

### Step 2：设计评测维度

- 这个产品的核心价值是什么？

- 从哪些维度衡量好坏？

- 先定3-5个核心维度，别一上来就搞十几个

### Step 3：设计评测用例

- 覆盖哪些场景？

- 按类型和难度分级

- 先写50-100条试水，再逐步扩充

### Step 4：确定评测方式

- 哪些可以用规则？

- 哪些可以用LLM Judge？

- 哪些必须人工评？

- 先从简单的开始，逐步完善

### Step 5：写Judge Prompt和Rubric

- 结构化的Judge Prompt

- 明确的评分标准（Rubric）

- 小规模验证一下准不准

### Step 6：跑基线评测

- 用当前版本跑一遍全量评测

- 得到基线数据——这是你后续优化的参照点

- 把基线数据保存好（数据集版本+系统版本+全套指标）

### Step 7：失败归因分析

- 捞失败用例，做根因分类

- 找系统性问题——哪类失败最多？

- 排优化优先级

### Step 8：建黄金集

- 从评测用例中选最核心的

- 建Gate1/Gate2/Gate3三层

- 以后每次优化都跑回归测试

### Step 9：建立迭代闭环

```
评测 → 归因 → 优化 → 再评测 → 再归因 → 再优化
```

- 每次优化都要有数据支撑

- 每次版本都要有基线记录

- 持续迭代，越做越好

***

## 十一、常见坑 & 避坑指南

### 坑1：只看总分，不看维度分

**症状**："我们通过率95%，挺好的。"——但你不知道那5%是哪里错了。

**后果**：找不到优化方向，瞎试。

**避坑**：一定要拆维度，而且要做失败归因——知道错在哪，才能对症下药。

***

### 坑2：评测工具自己在变，结果不可比

**症状**：越优化分数越高，但用户反馈没变好。

**后果**：白忙活，自我感觉良好但实际没进步。

**避坑**：用复评基准——同一套评测基准，对所有历史版本重跑。

***

### 坑3：LLM Judge不准，你还以为它准

**症状**：Judge说新版本更好，人工一看反而更差。

**后果**：优化方向错了，越优化越糟糕。

**避坑**：

- 定期用人工抽检验证Judge的准确率

- 做位置偏置、量表遵从性、裕度分布三项检测

- 主观维度不要强上Judge，用人评

***

### 坑4：黄金集从来不更新

**症状**：黄金集还是半年前的，新功能一个都没覆盖。

**后果**：黄金集全绿，但新功能全是bug——测了等于没测。

**避坑**：

- 每个新功能上线，都要往黄金集里加对应的用例

- 每个Bug修复，都要加对应的回归用例

- 定期（比如每个季度）梳理一次黄金集的覆盖度

***

### 坑5：为了评测而评测

**症状**：搞了一大堆维度、一大堆用例、一大堆流程，但产品迭代速度反而慢了。

**后果**：评测成了负担，不是助力。

**避坑**：

- 评测是为了更好地迭代，不是为了做评测而做评测

- 初期可以简单点，先跑起来，再逐步完善

- 重点保障核心维度和核心路径，不要追求大而全

***

## 十三、下一个项目复用检查清单

做下一个AI项目的时候，照着这个清单走，评测体系直接搭起来：

- [ ] **Step 1**：明确评测目标（为什么测？给谁看？）

- [ ] **Step 2**：设计3-5个核心评测维度（跟核心价值挂钩）

- [ ] **Step 3**：写50-100条评测用例（覆盖主要场景，有类型和难度分级）

- [ ] **Step 4**：确定评测方式（哪些用规则？哪些用Judge？哪些人工？）

- [ ] **Step 5**：写Judge Prompt + Rubric（结构化、有明确评分锚点）

- [ ] **Step 6**：跑基线评测（保存好基线数据）

- [ ] **Step 7**：做第一次失败归因（找最核心的问题）

- [ ] **Step 8**：建Gate1黄金集（10-30条，快速回归）

- [ ] **Step 9**：开始迭代飞轮（评测→归因→优化→再评测）

- [ ] **Step 10**：逐步完善——扩充用例、增加维度、建Gate2/Gate3

***

## 最后一句话

**评测体系不是目的，迭代才是。**

评测是为了更快、更准地迭代——知道哪里有问题、知道优化有没有用、知道进步了多少。

不要为了做评测而做评测——让评测服务于迭代，这才是它的价值。
