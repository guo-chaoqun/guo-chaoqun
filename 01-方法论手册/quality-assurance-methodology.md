# AI产品质量保障体系方法论 · 操作手册

> 生成日期：2026.10.06
> 来源：电商客服RAG评测项目 + AI穿搭导购项目（627条断言体系提炼）
> 定位：AI产品的质量保障——断言驱动、黄金集回归、变异测试、质量门禁

---

## 为什么AI产品需要专门的质量保障？

传统软件的质量保障是"测试"——写测试用例，跑一下，绿了就过。

AI产品不一样——
- 输出是概率性的，没有绝对的"对"和"错"
- 模型本身就在不断变化（版本更新、微调）
- 同一个输入，可能输出不同的结果
- 你改了Prompt，可能导致100个地方变了

**传统的测试方法，搞不定AI产品的质量保障。**

AI产品的质量保障，需要一套专门的体系——
- 怎么衡量"好不好"？（评测体系）
- 怎么防止改坏旧功能？（黄金集回归）
- 怎么验证"测试本身靠不靠谱"？（变异测试）
- 怎么把控不同阶段的质量？（质量门禁）

> **没有质量保障的AI产品，就是在裸奔。**
> 每次改代码、每次改Prompt，你都不知道是变好了还是变差了。

---

## 一、质量保障体系全景

### 1.1 四层质量保障模型

```
┌──────────────────────────────────┐
│        L4 人工抽检/盲评           │  ← 最终质量把关
│     （主观质量、用户体验）         │
├──────────────────────────────────┤
│        L3 LLM Judge评测           │  ← 内容质量自动化评测
│     （要点覆盖、幻觉、相关性）     │
├──────────────────────────────────┤
│        L2 断言/规则检查           │  ← 确定性质量门禁
│     （格式、关键词、结构、逻辑）   │
├──────────────────────────────────┤
│        L1 单元/集成测试           │  ← 传统软件测试
│     （函数、接口、流程）          │
└──────────────────────────────────┘
```

| 层级 | 做什么 | 成本 | 速度 | 准确度 |
|------|------|------|------|--------|
| **L1 传统测试** | 代码逻辑、接口、流程 | 低 | 快 | 100% |
| **L2 断言/规则** | 输出格式、关键信息、逻辑约束 | 低 | 快 | 100%（能规则化的） |
| **L3 LLM Judge** | 内容质量、要点覆盖、幻觉 | 中 | 中 | 80-95%（看场景） |
| **L4 人工评测** | 主观质量、体验、可用性 | 高 | 慢 | 最高（但人也会犯错） |

**核心原则**：
> **能下层解决的，就不要推到上层。**
>
> 下层便宜、快速、准确——能规则化的，就用规则。
> 上层贵、慢，但能解决下层解决不了的问题。
> 四层结合，就是"又快又准又好"的质量保障体系。

---

### 1.2 AI产品的质量保障跟传统有什么不一样？

| 维度 | 传统软件测试 | AI产品质量保障 |
|------|-------------|--------------|
| **判断标准** | 非对即错 | 有程度之分（好/较好/一般/差） |
| **测试方法** | 断言 = 预期 == 实际 | 评测 = 打分/分类，有灰度 |
| **稳定性** | 同样的输入，同样的输出 | 同样的输入，输出可能不一样 |
| **覆盖范围** | 测功能点 | 测效果、体验、安全性……维度更多 |
| **工具** | 单元测试框架、E2E测试 | 评测框架、LLM Judge、人工标注平台 |
| **核心挑战** | 覆盖度够不够 | 评测准不准、能不能防回归 |

## 二、断言驱动开发：AI产品的确定性防线

### 2.1 什么是断言驱动？

> **对AI的输出，用断言来检查"它至少不能错什么"。**

AI的输出是概率性的，你不能要求它"100%准确"。但你可以要求它——
- 格式不能错（必须是JSON，不能少字段）
- 关键信息不能少（必须包含XX要点）
- 不能说不该说的话（不能有违禁词）
- 逻辑不能自相矛盾（不能同时说A和非A）

这些"必须满足的底线"，就用断言来检查。

**断言 = AI输出的"及格线"——过了断言不一定好，但没过断言一定不行。**

---

### 2.2 断言的类型

| 类型 | 检查什么 | 例子 |
|------|---------|------|
| **格式断言** | 输出格式对不对 | 是不是有效的JSON？有没有必填字段？ |
| **内容断言** | 关键信息有没有 | 有没有包含"7天无理由"？ |
| **结构断言** | 结构对不对 | 是不是分了三段？有没有标题？ |
| **逻辑断言** | 逻辑自洽吗 | 有没有自相矛盾？ |
| **安全断言** | 有没有违规内容 | 有没有违禁词？有没有泄露隐私？ |
| **约束断言** | 有没有违反业务规则 | 退款金额不能大于支付金额 |
| **长度断言** | 长度合不合适 | 不能少于50字，不能超过500字 |

---

### 2.3 断言怎么写？

**基本结构**：
```python
def assert_output_valid(output):
    # 格式断言：必须是有效的JSON
    data = json.loads(output)

    # 内容断言：必须包含关键字段
    assert "answer" in data, "缺少answer字段"
    assert "sources" in data, "缺少sources字段"

    # 长度断言：回答不能太空
    assert len(data["answer"]) > 20, "回答太短"

    # 安全断言：不能有违禁词
    assert not contains_forbidden_words(data["answer"]), "包含违禁内容"

    # 逻辑断言：引用的来源必须在检索结果中
    assert all_sources_exist(data["sources"], retrieved_docs), "引用了不存在的来源"
```

**好的断言的特点**：
1. **明确**——通过/失败的标准清晰，没有歧义
2. **独立**——每个断言只检查一件事
3. **可定位**——失败了能说清楚"哪里错了"
4. **有层次**——核心断言（必须过）和次要断言（尽量过）分开

---

### 2.4 断言的"度"：不要过度断言

断言不是越多越好。

**断言太多的问题**：
- 维护成本高——改一点东西，一堆断言要改
- 误杀率高——其实内容没问题，但格式/措辞稍有不同就挂了
- 限制创新——AI输出被框死了，缺少灵活性

**怎么把握度？**

| 断言级别 | 说明 | 通过率要求 |
|---------|------|-----------|
| **P0 必须过** | 核心功能、安全合规 | 100% |
| **P1 尽量过** | 重要的质量要求 | 95%+ |
| **P2 参考** | 优化建议、锦上添花 | 不强制 |

**P0的断言宁缺毋滥**——只有"绝对不能错"的东西，才放在P0。
P0太多，等于没有P0——因为你总会被迫"放宽"一些。

## 三、黄金集：回归测试的基石

### 3.1 什么是黄金集？

> **黄金集 = 一套固定的、经过验证的测试用例 + 预期标准。**

每次改代码、改Prompt、换模型，都用黄金集跑一遍——
- 全绿 → 放心，没搞坏旧功能
- 红了 → 糟糕，有回归，赶紧修

**为什么叫"黄金"？**
- 因为它是你质量保障的"硬通货"——有了它，你改代码就有底气
- 它是精心挑选的、有代表性的——不是随便找的

---

### 3.2 黄金集怎么建？

#### Step 1：选用例

从哪里选？
- 核心功能的典型场景（每个功能至少一条）
- 历史上出过问题的Bad Case（防止重犯）
- 边界场景（容易出错的地方）
- 安全/合规场景（红线）

选多少？
- **小型（Gate1）**：10-30条 —— 快速检测，每次提交必跑
- **中型（Gate2）**：50-100条 —— 版本合并前跑
- **大型（Gate3）**：全量（300+） —— 正式发布前跑

---

#### Step 2：定标准

每条用例要有明确的"通过标准"：
- 格式标准（必须是什么格式）
- 内容标准（必须包含什么信息）
- 质量标准（达到什么质量水平）
- 安全标准（不能有什么内容）

标准怎么定？
- 能规则化的 → 写断言
- 不能规则化的 → 用LLM Judge评
- 主观的 → 人工标"金标准"答案

---

#### Step 3：验证有效性

黄金集建好了，还要验证一下——它真的能测出问题吗？

怎么验证？——**变异测试**（见下一章）。
- 故意在代码里植入错误
- 看黄金集能不能测出来
- 如果能测出来 → 黄金集有效
- 如果测不出来 → 黄金集有漏洞，需要补

---

### 3.3 黄金集的维护

黄金集不是建完就完事了，它需要持续维护：

| 事件 | 要做什么 |
|------|---------|
| **新功能上线** | 加对应的测试用例到黄金集 |
| **Bug修复** | 加对应的回归用例到黄金集（"疫苗"） |
| **需求变更** | 更新对应的用例和标准 |
| **定期审核** | 检查用例是不是过时了、有没有重复 |

**一个好的黄金集，会随着产品一起成长——越用越大，越用越全。**

## 四、变异测试：验证"测试本身靠不靠谱"

### 4.1 为什么需要变异测试？

你写了100条断言，全绿了——但你怎么知道这些断言是有用的？

会不会——
- 代码全错了，断言还全绿？
- 有些断言是"永真"的，怎么测都会过？
- 有些断言太松了，小错误根本测不出来？

**变异测试就是回答这个问题的——你的测试，真的能测出bug吗？**

---

### 4.2 变异测试的原理

```
1. 故意在代码里植入错误（"变异"）
   ↓
2. 跑测试
   ↓
3. 如果测试能测出这个错误（变红）→ 测试有效（"杀死"了变异）
   如果测试没测出来（还是绿的）→ 测试有漏洞（变异"存活"了）
   ↓
4. 变异测试通过率 = 被杀死的变异数 / 总变异数
```

**通过率越高，说明你的测试越靠谱。**

- 通过率 90%+ → 测试很靠谱
- 通过率 70-90% → 还行，但有提升空间
- 通过率 < 70% → 测试质量堪忧，很多bug测不出来

---

### 4.3 常见的变异类型

| 变异类型 | 说明 | 例子 |
|---------|------|------|
| **值变异** | 改数值 | 5 → 10，0.5 → 0.8 |
| **条件变异** | 改判断条件 | > → >=，== → != |
| **语句删除** | 删掉一行代码 | 删一行校验逻辑 |
| **返回值变异** | 改返回值 | return true → return false |
| **变量替换** | 换变量名 | a → b |
| **运算符变异** | 改运算符 | + → -，&& → \|\| |
| **Prompt变异** | 改Prompt内容 | 删掉一条指令、改一个词 |

**AI产品特有的变异类型**：Prompt变异——故意改坏Prompt，看评测体系能不能测出效果下降。

---

### 4.4 实战案例：断言的可证伪性

穿搭项目做了完整的变异测试——60+把"变异刀"，从各个角度植入错误，看断言能不能测出来。

**发现了什么？**

1. **永真断言**：有些断言不管代码怎么错，都是绿的——写了等于没写
2. **太松的断言**：小错误测不出来——只有大错才会红
3. **覆盖不到的地方**：有些功能点，完全没有断言——出了问题根本发现不了

**然后怎么做？**
- 永真断言 → 删掉或者重写
- 太松的断言 → 加严
- 覆盖不到的 → 补断言

**结论**：
> **"判据能不能证伪"是最该先做的事。**
>
> 不能证伪的断言，写了等于没写——只是给自己心理安慰而已。
>
> 先验证测试本身靠不靠谱，再谈测试覆盖率。

---

### 4.5 变异测试什么时候做？

不是每次提交都要做——变异测试成本高，跑一次慢。

**建议的频率**：
- 重大版本更新前 → 做一次全面的
- 测试体系大改之后 → 验证一下新的测试体系
- 定期（比如每个季度） → 检查测试质量有没有下降
- 出了线上bug之后 → 看看为什么测试没测出来，补测试，再变异验证

## 五、三层质量门禁

### 5.1 什么是质量门禁？

> **不同的阶段，跑不同级别的测试，达到不同的质量标准，才能进入下一阶段。**

就像门禁——没有达到标准，就不让过。

```
开发提交 → Gate1（快速门禁）→ 合并到开发分支
              ↓ 通过
           Gate2（标准门禁）→ 合并到主干
              ↓ 通过
           Gate3（全量门禁）→ 正式发布
```

---

### 5.2 三层门禁详解

| 门禁 | 级别 | 用例数 | 耗时 | 什么时候跑 | 通过标准 |
|------|------|--------|------|-----------|---------|
| **Gate1** | 快速 | 10-30条 | 几秒-几分钟 | 每次提交代码/Prompt | 所有P0断言全绿 |
| **Gate2** | 标准 | 50-100条 | 几十分钟 | 版本合并前、PR提交时 | P0全绿 + P1通过率 ≥ 95% + 核心指标不下降 |
| **Gate3** | 全量 | 300条+ | 几小时 | 正式发布前 | P0全绿 + P1通过率 ≥ 98% + 核心指标达标 + 人工抽检通过 |

**为什么要分层？**
- 全量跑一次很贵、很慢——不能每次都跑
- 但每次都不跑，又怕搞坏了东西
- 分层就是平衡——小改动跑Gate1，重要改动跑Gate2，发布前跑Gate3

---

### 5.3 门禁通过标准怎么定？

不是拍脑袋定的，要考虑：
1. **产品阶段**——早期可以松一点，成熟期要严
2. **业务性质**——高风险场景（金融、医疗）要严，娱乐场景可以松
3. **团队能力**——测试体系还不完善的时候，标准定太高也没用
4. **历史基线**——看看历史上的通过率是多少，在此基础上逐步提高

**定标准的原则**：
- 跳一跳够得着——不能太松（没意义），也不能太紧（总是过不了）
- 逐步提高——先从80%开始，做到了再提到90%，再到95%
- 不同级别分开定——P0必须100%，P1可以95%，P2可以90%

---

### 5.4 门禁挂了怎么办？

门禁挂了，说明有问题——不能强行通过。

**处理流程**：
1. **定位问题**——哪些用例挂了？什么原因？
2. **判断严重程度**——是P0还是P1？影响多大？
3. **修或者回滚**——
   - 能快速修的 → 修了重跑
   - 修起来麻烦的 → 先回滚，下次再上
4. **加回归用例**——修好了之后，把这个问题加入黄金集，防止再犯

**绝对不能做的事**：
- 强行跳过门禁 → 那要门禁还有什么用？
- 改测试用例来"凑通过" → 自欺欺人，最后坑的是自己

## 六、复评基准：解决评测污染问题

### 6.1 什么是评测污染？

你优化了Judge的Prompt，然后用新Judge去测新版本，发现分数提升了——但你不知道是系统真的变好了，还是Judge变松了。

这就是**评测污染**——评测工具本身变了，导致不同版本的结果不可比。

**为什么这是个大问题？**
- 你以为自己在进步，其实只是评测标准在变松
- 越优化分数越高，但用户反馈没变好
- 最后你活在自己的"分数幻觉"里

---

### 6.2 怎么解决？——复评基准

> **用同一版本的评测工具，对所有历史版本重新跑一遍评测。**

```
时间线：
  V1版本 → 用Judge v1评测 → 分数 85分
  V2版本 → 用Judge v2评测 → 分数 90分  ❌ 不可比！

复评后：
  V1版本 → 用Judge v2重评 → 分数 87分
  V2版本 → 用Judge v2评测 → 分数 90分  ✅ 可比！
  真实提升：3分，不是5分
```

**为什么重要？**
- 确保所有版本在同一把尺子下比较
- 看到真实的进步曲线
- 避免"自我感觉良好但实际没进步"的假象

---

### 6.3 复评基准怎么落地？

1. **保存历史版本**——每个重要版本的代码/Prompt都要保存
2. **保存评测基准**——每个版本的评测工具（Judge Prompt、Rubric）也要保存
3. **定期复评**——评测工具更新了，就对所有历史版本重跑一遍
4. **画进步曲线**——把每个版本的分数画成曲线，看真实的进步趋势

**保存的内容**：
- 代码版本（Git commit hash）
- Prompt版本号
- 评测基准版本（Judge Prompt + Rubric版本）
- 评测结果（全量数据，不是只有总分）

## 七、数据飞轮：让质量体系自我进化

### 7.1 什么是质量数据飞轮？

> **每发现一个问题，就加一支"疫苗"——测试越来越全，质量越来越稳。**

```
发现问题 → 定位根因 → 修复 → 加测试用例 → 加入黄金集 → 下次不会再犯
     ↑                                                  │
     └──────────────────────────────────────────────────┘
```

每转一圈，黄金集就多一条用例，质量保障就多一层。
转得越多，体系越完善——到最后，大部分常见问题都能被测出来。

---

### 7.2 问题从哪来？

| 来源 | 说明 | 处理方式 |
|------|------|---------|
| **测试发现** | 黄金集跑出来的失败用例 | 修Bug + 加更细的断言 |
| **用户反馈** | 用户投诉、差评 | 复现问题 + 加回归用例 |
| **线上监控** | 错误率上升、指标异常 | 定位问题 + 加监控 + 加测试 |
| **人工抽检** | 人工看的时候发现的问题 | 加入评测用例 |
| **安全审计** | 安全漏洞、合规问题 | 修复 + 加安全断言 |

**所有渠道发现的问题，最终都要变成"疫苗"——加入测试体系。**
不然下次还会犯同样的错。

---

### 7.3 让飞轮转起来的关键

1. **重视每一个问题**——哪怕是小问题，也要加回归用例。小问题攒多了就是大问题。
2. **自动化**——加用例、跑测试，尽量自动化。人工成本太高的话，飞轮转不起来。
3. **定期复盘**——每个迭代，看看新发现了多少问题、加了多少用例、测试覆盖率提升了多少。
4. **量化指标**——用数据说话：黄金集大小、断言数量、变异测试通过率、线上Bug率……

## 八、常见坑 & 避坑指南

### 坑1：断言写得太多，限制了AI的灵活性

**症状**：写了几百条断言，AI输出稍微有点不一样就挂了。结果AI被框死了，输出很死板。

**后果**：为了"质量"牺牲了体验——AI输出千篇一律，没有灵气。

**避坑**：断言分级——P0（必须过）少而精，P1/P2（尽量过）多一些。不要什么都放到P0。核心的、安全的东西用断言管，质量和体验的东西用评测管。

---

### 坑2：黄金集从来不更新

**症状**：黄金集还是半年前建的，新功能一个都没覆盖。

**后果**：黄金集全绿，但线上全是bug——测了等于没测。

**避坑**：建立机制——每个新功能上线、每个Bug修复，都要加对应的用例到黄金集。定期（每个季度）做一次覆盖度审核。

---

### 坑3：测试看起来很全，但其实测不出bug

**症状**：覆盖率90%+，断言几百条，但线上还是经常出问题。

**后果**：自我感觉良好，实际质量很差。

**避坑**：做变异测试——验证测试本身靠不靠谱。很多断言是"永真"的，写了等于没写。先把测试质量提上去，再谈覆盖率。

---

### 坑4：门禁形同虚设

**症状**：门禁挂了就强行过，或者改测试用例来凑通过。

**后果**：要门禁还有什么用？质量保障体系名存实亡。

**避坑**：门禁是红线，不能碰。挂了就修，修不了就回滚。如果门禁标准有问题，就改标准，但要走正式流程，不能每次都"特例"。

---

### 坑5：只看自动化测试，不做人工验证

**症状**："自动化测试全绿了，肯定没问题。"然后上线了用户骂。

**后果**：自动化测的都是"底线"——格式对不对、有没有违禁词。但内容质量好不好、体验顺不顺，自动化测不出来。

**避坑**：自动化测试是基础，但不是全部。重要版本发布前，一定要有人工抽检或者盲评。

---

## 十、下一个项目复用检查清单

做下一个项目的时候，照着这个清单建质量保障体系：

### 基础建设
- [ ] 有单元/集成测试吗？（L1，传统测试）
- [ ] 有断言体系吗？（L2，格式/内容/安全/逻辑断言）
- [ ] 断言分级了吗？（P0/P1/P2）
- [ ] 有LLM Judge评测吗？（L3，内容质量）
- [ ] 有人工抽检机制吗？（L4，主观质量）

### 黄金集与回归
- [ ] 建了Gate1黄金集吗？（10-30条，快速回归）
- [ ] 建了Gate2黄金集吗？（50-100条，标准回归）
- [ ] 建了Gate3全量评测吗？（发布前全量跑）
- [ ] 三层质量门禁跑起来了吗？
- [ ] 门禁通过标准定了吗？

### 测试质量验证
- [ ] 做过变异测试吗？（验证测试本身靠不靠谱）
- [ ] 变异测试通过率是多少？
- [ ] 有"永真断言"吗？（发现了就删掉或重写）
- [ ] 评测体系本身有验证吗？（位置偏置、量表遵从性、一致性）

### 评测基准
- [ ] 保存历史版本吗？（代码/Prompt/评测工具）
- [ ] 做复评基准吗？（评测工具更新了，对历史版本重跑）
- [ ] 有进步曲线吗？（每个版本的分数变化）

### 数据飞轮
- [ ] 每个Bug修复都加回归用例吗？（"疫苗"机制）
- [ ] 新功能上线都加测试用例吗？
- [ ] 用户反馈的问题都加入测试集吗？
- [ ] 定期复盘质量指标吗？（黄金集大小、断言数、变异通过率、线上Bug率）

### 常见坑自查
- [ ] 断言是不是太多了？（会不会限制AI的灵活性）
- [ ] 黄金集是不是从来不更新？（有没有覆盖新功能）
- [ ] 门禁是不是形同虚设？（挂了是不是强行过）
- [ ] 只看自动化，不做人工验证吗？

## 最后一句话

**质量保障不是写多少测试，而是建立一套能自我进化的体系。**

测试本身也需要被测试。
质量体系也需要持续优化。

当每一个问题都能变成一支"疫苗"的时候——
你的质量保障体系，就真正活起来了。
