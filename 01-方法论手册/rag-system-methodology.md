## 什么是RAG？

**RAG = Retrieval-Augmented Generation（检索增强生成）**

简单说就是：

> 先从知识库中检索相关内容，然后让大模型基于检索到的内容生成回答。

为什么需要RAG？因为大模型有两个天生的问题：

1. **知识过时**——训练数据是截止到某个时间点的，最新的信息它不知道
2. **领域知识缺失**——你公司内部的文档、产品手册、客服话术，大模型没学过

RAG就是解决这两个问题的——把你的知识库接进去，让大模型"查资料"之后再回答。

> **大模型 = 聪明的大脑**
> **RAG = 给大脑配一个可以随时查阅的图书馆**

***

## 一、RAG全景：从0到1的完整链路

### 1.1 RAG系统的4个核

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  数据处理层   │ →   │  检索层     │ →   │  上下文组装 │ →   │  生成层     │
│ （知识库建设）│     │ （找相关内容）│     │ （拼装Prompt）│     │ （生成回答） │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
```

| 模块        | 做什么                  | 关键问题     |
| --------- | -------------------- | -------- |
| **数据处理层** | 把文档切成合适的块、向量化、存到向量库  | 怎么切？切多大？ |
| **检索层**   | 根据用户问题，从知识库中找到最相关的内容 | 怎么找？找多少？ |
| **上下文组装** | 把检索到的内容和用户问题拼成Prompt | 怎么拼效果最好？ |
| **生成层**   | 大模型基于上下文生成回答         | 怎么让它不胡说？ |

***

### 1.2 进阶：三层漏斗架构

基础的RAG是"检索→生成"两段式。但稍微复杂一点的场景，就需要**三层漏斗架构**：

```
用户提问
   ↓
┌─────────────┐
│  意图识别层   │  ← 先搞清楚：用户要干嘛？
│  （分类）    │     属于哪个业务分支？
└──────┬──────┘
       ↓ 分到对应的分支
┌─────────────┐
│  路由/检索层  │  ← 在对应分支的知识库里找
│  （找内容）   │
└──────┬──────┘
       ↓ 拿到相关内容
┌─────────────┐
│  生成/执行层  │  ← 生成回答 或 执行动作
│  （输出）    │
└──────┬──────┘
       ↓
   返回给用户
```

**为什么要三层？而不是两层？**

| 优点         | 说明                               |
| ---------- | -------------------------------- |
| **检索更准**   | 先分类再检索——只在相关分支的知识库找，不会被其他分支的内容干扰 |
| **每层独立优化** | 分类器优化分类器，检索优化检索，生成优化生成——出了问题也好定位 |
| **可扩展性好**  | 新增一个业务分支，加一个分类标签、加一个知识库就行，不影响其他  |
| **可执行动作**  | 有些分类不需要生成，直接执行动作（比如"查订单"→调订单接口）  |

**实战案例（电商客服RAG）**：

> 6个业务分支：基础闲聊、售前咨询、退换货规则、退款时效、物流查询、投诉建议
>
> 第一层：意图分类器——把用户问题分到这6类中的某一类
> 第二层：路由检索——如果是退换货，就去退换货知识库找；如果是退款，就去退款知识库找
> 第三层：生成回答——基于检索到的内容，生成准确的回答
>
> 为什么不直接全库检索？因为6个分支的内容混在一起，容易检索错——比如用户问"退款要多久"，可能检索到"7天无理由退换"的内容，看起来相关但其实不对。
>
> 先分类再检索，准确率高很多。

## 二、数据处理层：知识库怎么建？

### 2.1 数据从哪来？

| 来源类型      | 例子            | 特点              |
| --------- | ------------- | --------------- |
| **结构化文档** | 产品手册、FAQ、政策文档 | 质量高、格式规范，最适合RAG |
| **半结构化**  | 表格、JSON、数据库   | 需要特殊处理才能切分      |
| **非结构化**  | 对话记录、文章、网页    | 质量参差不齐，需要清洗     |
| **多模态**   | 图片、PDF扫描件     | 需要OCR转文字        |

**最佳实践**：

- 优先用结构化的、质量高的文档

- 低质量的内容不要往知识库里塞——垃圾进，垃圾出

- 知识库不是越大越好，是越准越好

***

### 2.2 切片策略：切多大？怎么切？

切片（Chunking）是RAG最基础也最容易踩坑的地方。

**切片大小的权衡**：

- 切太小 → 信息不完整，检索到了也看不懂

- 切太大 → 噪音多，无关内容也带进来了，而且占Token

| 切片大小             | 优点         | 缺点           | 适用场景       |
| ---------------- | ---------- | ------------ | ---------- |
| **小（100-300字）**  | 精准、相关性高    | 信息不完整、上下文缺失  | FAQ、短句、知识点 |
| **中（300-800字）**  | 平衡，大多数场景够用 | 中庸，没什么突出的    | 通用文档、产品手册  |
| **大（800-2000字）** | 信息完整、上下文充分 | 噪音多、Token消耗大 | 长文档、复杂内容   |

**没有"最好的"切片大小——要看你的文档类型和使用场景。**

常用的经验值：

- FAQ类：50-200字一条，一条就是一个完整的问答对

- 产品手册：300-500字一段，按段落切

- 长文章：500-1000字一段，按章节切

***

### 2.3 切片方法

| 方法         | 说明               | 优点      | 缺点         |
| ---------- | ---------------- | ------- | ---------- |
| **固定长度切片** | 按字数/Token数切，最简单  | 简单、快    | 可能把完整的意思切开 |
| **按结构切片**  | 按标题/段落/列表切       | 保留语义完整性 | 需要文档有结构    |
| **语义切片**   | 用语义相似度判断，语义变了就切  | 最智能、最合理 | 慢、贵、需要调参数  |
| **递归切片**   | 先按大结构切，太大了再按小结构切 | 灵活、平衡   | 实现复杂一点     |

**推荐做法**：

- 如果你的文档有明确的结构（标题、段落）——按结构切，效果最好

- 如果文档没什么结构（一大段文字）——固定长度+重叠（比如500字一块，重叠50字）

- 语义切片听起来酷，但实际用起来性价比不高——调参数很麻烦，提升有限

***

### 2.4 切片的进阶技巧

#### 技巧1：重叠（Overlap）

两块之间留一点重叠，防止关键信息刚好在切分线上被切断。

```
[块1：第1-500字]
        [第450-950字：块2]
                [第900-1400字：块3]
```

重叠多少合适？——大概切片大小的10%左右。比如500字的块，重叠50字。

***

#### 技巧2：元数据（Metadata）

每个切片除了正文，还要附带上元数据：

- 来源文档标题

- 章节标题

- 页码/位置

- 分类标签

- 最后更新时间

**为什么重要？**

- 检索的时候可以过滤（比如只搜某个分类的）

- 生成回答的时候可以引用来源

- 更新知识库的时候知道哪些是旧的

***

#### 技巧3：分层切片

一篇文档，切两层：

- 大块：按章节切，每章一块（信息完整）

- 小块：每段一块（检索精准）

检索的时候先搜小块，找到相关的段落，再把对应的整章内容拿出来给大模型。

这样既有检索的精准性，又有上下文的完整性。

***

### 2.5 向量化：Embedding模型怎么选？

切片之后，要把文字转成向量（Embedding），存在向量数据库里，才能做相似度检索。

**选Embedding模型看什么？**

| 维度       | 说明           | 重要性         |
| -------- | ------------ | ----------- |
| **效果**   | 检索准不准        | ⭐⭐⭐⭐⭐ 最重要   |
| **速度**   | 生成向量快不快      | ⭐⭐⭐ 中等      |
| **成本**   | 多少钱/1K Token | ⭐⭐ 次要       |
| **维度**   | 向量的维度数       | ⭐ 影响存储和检索速度 |
| **语言支持** | 中文效果好不好      | ⭐⭐⭐⭐ 很重要    |

**常见的选择**：

- **OpenAI text-embedding-3-small**：效果好、便宜、英文强，中文也还行

- **OpenAI text-embedding-ada-002**：经典款，效果稳定，稍贵一点

- **bge-large-zh**：中文效果好，开源，可以本地部署

- **m3e**：中文效果不错，开源，轻量

**经验建议**：

- 不差钱、用英文为主 → OpenAI的

- 中文场景、想省钱 → bge或m3e

- 数据敏感、不能外传 → 开源模型本地部署

***

### 2.6 知识库建设的常见坑

#### 坑1：垃圾进，垃圾出

**症状**：什么内容都往知识库里塞——过期的、错误的、重复的、质量差的。

**后果**：检索到的内容质量差，生成的回答自然也好不了。

**避坑**：知识库入库之前做质量审核。过期的删掉、错误的改掉、重复的合并。宁缺毋滥。

***

#### 坑2：知识库不更新

**症状**：知识库建完就不管了，内容还是半年前的。

**后果**：回答的都是过时的信息，用户越来越不信。

**避坑**：建立知识库更新机制。产品更新了、政策变了，知识库要同步更新。定期（比如每个季度）做一次全量审核。

***

## 三、检索层：怎么找到最相关的内容？

### 3.1 检索的核心问题

检索层要回答两个问题：

1. **找多少？**（Top K = ?）
2. **怎么判断"相关"？**（相似度阈值 = ?）

这两个参数直接决定了RAG的效果——

- 找太少 → 信息不够，回答不完整

- 找太多 → 噪音多，反而干扰模型，而且费Token

- 阈值太低 → 不相关的也塞进来，效果变差

- 阈值太高 → 相关的被过滤掉了，回答不上来

**这两个参数不是拍脑袋定的，是测出来的。**

***

### 3.2 Top K 怎么定？

**测试方法**：

1. 准备一批评测用例（有标准答案的）
2. 分别用 K=1, 2, 3, 5, 8, 10 跑评测
3. 看哪个K值的效果最好

**一般规律**：

- K太小 → 召回率低，信息不够

- K太大 → 精确率下降，噪音增多

- 中间有个"甜点"——再增加K，效果不升反降

**经验参考**：

- FAQ类、短回答场景：K=2-4

- 复杂问答、长文档场景：K=4-8

- 超过10的话，通常是收益递减，甚至反效果

***

### 3.3 相似度阈值怎么定？

相似度阈值——检索分数低于这个值的，就认为"不相关"，不要塞给模型。

**为什么需要阈值？**

- 如果知识库中根本没有相关内容，检索也会返回"最相似"的结果——但其实完全不相关

- 这时候把不相关的内容塞给模型，模型可能会基于错误的内容生成回答——还不如直接说"我不知道"

**怎么定阈值？**

1. 准备评测用例，标记哪些知识库中有答案、哪些没有
2. 跑检索，记录每条的相似度分数
3. 找一个阈值——高于这个值的，大部分是真相关；低于的，大部分是不相关
4. 用这个阈值做截断

**权衡**：

- 阈值设高了 → 过滤得多，漏掉一些相关的（召回率低）

- 阈值设低了 → 漏得多，塞进来一些不相关的（精确率低）

- 看你的产品更怕哪种——怕答错就设高一点（宁缺毋滥），怕答不上来就设低一点

***

### 3.4 检索方式：不止向量检索

很多人以为RAG的检索就是"向量相似度检索"。其实检索方式有好几种，各有优劣。

| 检索方式      | 原理            | 优点           | 缺点            |
| --------- | ------------- | ------------ | ------------- |
| **关键词检索** | 关键词匹配（BM25）   | 快、准、对专有名词效果好 | 不理解语义，同义词匹配不上 |
| **向量检索**  | 语义相似度         | 理解语义，同义词也能匹配 | 对专有名词、数字不敏感   |
| **混合检索**  | 关键词 + 向量，结果融合 | 两者的优点都有      | 实现复杂，权重要调     |

**最佳实践：混合检索**

- 关键词检索负责"精确匹配"——专有名词、数字、型号这些

- 向量检索负责"语义匹配"——意思相近但用词不一样的

- 两个结果融合之后，再排序取Top K

效果通常比单用一种好10-20%。

***

### 3.5 检索重排序（Rerank）

检索出来的Top K，可能排序不是最优的。这时候可以用Rerank模型重新排一下序。

**为什么需要Rerank？**

- 向量检索是"粗筛"——快，但不是最准

- Rerank模型是"精排"——慢一点，但更准

- 先粗筛出Top 20，再精排选出Top 5，效果比直接Top 5好

**代价**：

- 多一步推理，增加延迟

- 多花一份钱（Rerank API的费用）

**什么时候值得加Rerank？**

- 对检索准确率要求高的场景

- 知识库内容多、相似度高，不容易区分的

- 如果Top 5-10已经够好了，就没必要加

***

### 3.6 检索优化的实操步骤

1. **建评测集**：准备有标准答案的问答对，用来测检索效果
2. **测基线**：用默认参数（比如K=5，向量检索）跑一遍，看召回率
3. **调参数**：调Top K、调阈值，找最优值
4. **加混合检索**：加上关键词检索，跟向量检索融合，看有没有提升
5. **加重排序**：如果还不够，加Rerank
6. **找到甜点就停**：不要过度优化，边际收益递减

## 四、上下文组装：怎么拼Prompt？

### 4.1 为什么上下文组装很重要？

检索到了相关内容，但怎么把它"喂"给大模型，也很有讲究。

拼得好 → 模型能准确理解内容，回答质量高
拼得不好 → 模型找不到重点，或者被噪音干扰，回答质量差

***

### 4.2 标准Prompt结构

一个好的RAG Prompt，通常包含这几个部分：

```
【系统指令】
你是一个XX助手，负责XX。请根据提供的参考资料回答用户的问题。
回答要求：
1. 只基于参考资料回答，不要编造
2. 如果参考资料中没有答案，就说"抱歉，我暂时无法回答这个问题"
3. ...（其他要求）

【参考资料】
1. （来源：文档A）
   检索到的内容第一段...

2. （来源：文档B）
   检索到的内容第二段...

【用户问题】
{user_question}

【回答】
```

***

### 4.3 组装的几个要点

#### 要点1：明确指令——"只基于参考资料回答"

一定要在Prompt里强调——只能用参考资料里的内容，不要自己编造。

**为什么重要？**

- 不强调的话，模型会把自己的知识和检索到的内容混在一起说

- 混进去的部分可能是错的（幻觉）

- 明确说了"只基于参考资料"，幻觉率会低很多

***

#### 要点2：给检索内容编号、标来源

- 每一段检索内容编上号

- 标出来源（哪篇文档、哪个章节）

**好处**：

- 模型更容易区分不同的内容

- 生成回答的时候可以引用来源（"根据文档A"）

- 用户也能追溯答案的出处

***

#### 要点3：相关的放前面

研究表明，模型对**开头和结尾**的内容注意力更高，中间的容易忽略（"U型注意力"）。

所以——把最相关的内容放在最前面，次相关的放后面。

如果检索结果是按相似度排序的，那直接按顺序放就行（最相关的在最前面）。

***

#### 要点4：控制长度，别塞满上下文窗口

不要把所有检索到的内容都一股脑塞进去——

- Token消耗大，贵

- 噪音多，模型容易被干扰

- 可能超过上下文窗口限制

**控制在多少合适？**

- 一般来说，上下文内容占模型窗口的1/4到1/3比较合适

- 比如8K窗口的模型，上下文内容控制在2K-3K Token

- 留足够的空间给对话历史和生成的回答

***

### 4.4 引用溯源的实现

如果你的产品需要"告诉用户答案从哪来"，有两种做法：

| 做法           | 说明                          | 优点        | 缺点             |
| ------------ | --------------------------- | --------- | -------------- |
| **Prompt引导** | 在Prompt里让模型回答的时候标注引用来源      | 简单，不用额外开发 | 模型可能标错，不是100%准 |
| **后处理匹配**    | 生成回答之后，用规则匹配回答内容和检索内容，自动标来源 | 准确、可控     | 实现复杂一点         |

**推荐**：Prompt引导 + 后处理校验。

- Prompt里让模型标引用

- 后处理的时候检查一下——引用的内容真的在对应的来源里吗？

- 对不上的，修正或者去掉

## 五、生成层：怎么让模型答得好？

### 5.1 生成层的核心目标

1. **准确**——基于知识库，不编造
2. **完整**——覆盖所有关键信息点
3. **合规**——不说不该说的话
4. **自然**——像人说的话，不是机器味

这四个目标有时候是矛盾的——比如越准确，可能越生硬；越自然，可能越容易幻觉。

**产品经理的工作，就是在这些目标之间找平衡。**

***

### 5.2 降低幻觉的几种方法

| 方法         | 说明                       | 效果 | 成本 |
| ---------- | ------------------------ | -- | -- |
| **明确指令**   | Prompt里强调"只基于参考资料，不要编造"  | 中  | 零  |
| **检索质量提升** | 检索越准，幻觉越少                | 高  | 中  |
| **置信度判断**  | 检索分数低的，直接走兜底             | 高  | 低  |
| **后置校验**   | 生成之后检查有没有编造内容            | 高  | 中  |
| **调温度参数**  | temperature设低一点（0.1-0.3） | 中  | 零  |
| **引用溯源**   | 强制标注来源，模型会更谨慎            | 中  | 低  |

**注意**：没有任何一种方法能100%消除幻觉。组合使用多种方法，才能把幻觉率降到可接受的水平。

***

### 5.3 温度参数（Temperature）怎么设？

Temperature控制模型输出的"随机性"——

- 越高 → 越随机、越有创意、越容易胡说八道

- 越低 → 越确定、越保守、越不容易出错

**不同场景的推荐值**：

| 场景        | 推荐Temperature | 为什么             |
| --------- | ------------- | --------------- |
| **问答/客服** | 0.1 - 0.3     | 要准确，不能胡说        |
| **摘要/总结** | 0.2 - 0.5     | 要忠实原文，但可以稍微灵活一点 |
| **写作/创意** | 0.7 - 1.0     | 要创意、要多样性        |
| **闲聊/陪伴** | 0.8 - 1.2     | 要有趣、要不死板        |

**核心原则**：

> **容错空间越低，温度就越低。**
>
> 答错了后果很严重的场景——温度往低了设
> 答错了也没什么大不了的——温度可以高一点

***

### 5.4 生成层的验证指标

怎么衡量生成层的效果？——看这些指标：

| 指标        | 说明              | 怎么测              |
| --------- | --------------- | ---------------- |
| **要点覆盖率** | 回答有没有覆盖所有关键信息点  | 人工评测 / LLM Judge |
| **幻觉率**   | 有没有编造参考资料中没有的内容 | 人工评测 / LLM Judge |
| **违规率**   | 有没有说不该说的话       | 规则检查 + 人工抽检      |
| **相关性**   | 回答跟问题对不对得上      | LLM Judge        |
| **自然度**   | 像不像人说的话         | 人工评测             |

这些指标就是评测体系里"模型层"的核心指标——具体怎么测，参考《评测体系方法论》。

***

## 六、进阶：RAG优化的完整方法论

### 6.1 三层失败模型

RAG系统出了问题，先定位是哪一层的问题：

```
用户提问 → 分类 → 检索 → 生成 → 回答
            ↓      ↓      ↓
         L1失败  L2失败  L3失败
       （分错类）（找错了）（不会说）
```

| 层级         | 失败类型             | 表现                 | 优化方向                              |
| ---------- | ---------------- | ------------------ | --------------------------------- |
| **L1 分类层** | 意图分类错误           | 分到了错误的业务分支         | 优化分类器、增加训练数据、优化分类Prompt           |
| **L2 检索层** | 检索不到 / 检索不准      | 知识库有，但没找到；或者找到了但不对 | 优化切片策略、换Embedding模型、加混合检索、加Rerank |
| **L3 生成层** | 幻觉 / 表述问题 / 格式错误 | 找到了正确内容，但生成得不对     | 优化Prompt、调温度、加后置校验                |

**为什么要分层定位？**

- 不知道问题出在哪一层，就不知道该优化什么

- 比如回答不对——可能是分类错了，可能是检索错了，也可能是生成错了

- 每一层的优化方法完全不一样

***

### 6.2 归因分析实操

1. **收集失败用例**：所有没通过的用例
2. **逐条判断**：是哪一层的问题？（分类错？检索错？生成错？）
3. **统计占比**：各层失败的比例是多少？
4. **细分原因**：同一层里，具体是什么原因？

   - 分类层：相似意图混淆？边界场景？新意图？

   - 检索层：切片太大？Embedding不好？阈值太高？

   - 生成层：Prompt不好？温度太高？指令不明确？
5. **找杠杆点**：哪类问题最多？优化哪个收益最大？
6. **排优先级**：影响面 × 修复难度 → P0/P1/P2

**实战案例（客服项目）**：

> 43条失败用例归因：
>
> - 72.1% 跟分类器误路由有关（L1层）
>
> - 其余分散在检索、生成、用例问题
>
> ⇒ 最核心的问题是分类——把分类搞好了，大部分问题就解决了。
>
> 针对性优化之后，边界混淆场景准确率从63.6%提升到77.3%。

***

### 6.3 优化优先级

不是所有问题都要立刻修。用**影响面 × 修复难度**排优先级：

| 象限        | 优先级    | 例子                  |
| --------- | ------ | ------------------- |
| 影响大 × 成本低 | **P0** | 优化分类Prompt、调Top K参数 |
| 影响小 × 成本低 | **P1** | 修复个别错误的知识库内容        |
| 影响大 × 成本高 | **P2** | 换Embedding模型、加重排序   |
| 影响小 × 成本高 | **P3** | 自研切片算法、搞复杂的语义切片     |

**核心原则**：

> **先用最便宜的方法，拿到最大的收益。**
>
> 别一上来就搞最复杂的方案——先试试改Prompt、调参数，说不定效果就已经很好了。

***

### 6.4 迭代飞轮

```
评测 → 归因 → 优化 → 验证 → 下一轮
```

每一轮迭代：

1. 跑评测，看当前效果
2. 做归因，找最核心的问题
3. 针对性优化（一次只改一个变量）
4. 再跑评测，看有没有提升
5. 有提升 → 保留，进入下一轮
6. 没提升 → 回滚，换个方向试试

**每一轮迭代，你对系统的理解就深一层。**
转得越多，转得越快。

***

## 七、常见坑 & 避坑指南

### 坑1：知识库越大越好

**症状**：什么内容都往知识库里塞，觉得"知识库越大，回答越全面"。

**后果**：噪音多、检索不准、反而效果下降。而且维护成本高。

**避坑**：宁缺毋滥。只放高质量的、相关的内容。定期清理过期的、重复的、低质量的。

***

### 坑2：切片大小随便定

**症状**："大家都说500字好，那就500字吧。"

**后果**：可能切太小信息不完整，也可能切太大噪音多。效果不是最优的。

**避坑**：用你的数据、你的场景，实际测一下。不同的切片大小跑评测，看哪个效果最好。

***

### 坑3：只调生成层，不调检索层

**症状**：回答效果不好，就一个劲地改Prompt、换模型。

**后果**：其实问题出在检索层——检索到的内容根本不对，生成层再怎么调也没用。

**避坑**：先定位是哪一层的问题，再针对性优化。不要在错误的方向上使劲。

***

### 坑4：不做评测，凭感觉优化

**症状**："我觉得这样改了之后应该更好。"改完就上线了。

**后果**：可能确实更好，也可能更差——你不知道。

**避坑**：每次优化都要有数据验证。跑评测、看指标，确认真的提升了再上线。

***

### 坑5：一上来就搞最复杂的方案

**症状**："RAG要做就做最好的——混合检索+Rerank+多模态+GraphRAG，全上！"

**后果**：复杂度爆炸、成本很高、维护困难，但效果可能跟简单方案差不了多少。

**避坑**：从简单的开始——基础的向量检索+Prompt。跑通了，测一下效果。如果不够好，再加混合检索；还不够，再加Rerank；还不够，再考虑更复杂的方案。

> **不要一开始就造火箭。先造个自行车，能跑起来再说。**

***

## 九、下一个项目复用检查清单

做下一个RAG项目的时候，照着这个清单走：

### 知识库建设

- [ ] 数据来源梳理了吗？（哪些文档/哪些系统）

- [ ] 数据质量审核了吗？（过期的删了吗？错误的改了吗？）

- [ ] 切片策略定了吗？（切多大、怎么切、重叠多少）

- [ ] 切片大小实际测过吗？（不同大小跑评测，找最优值）

- [ ] Embedding模型选了吗？（效果/成本/语言支持）

- [ ] 元数据加了吗？（来源、分类、时间）

### 检索层

- [ ] Top K定了吗？（测过吗？）

- [ ] 相似度阈值定了吗？（测过吗？）

- [ ] 检索方式选了吗？（向量/关键词/混合）

- [ ] 需要加Rerank吗？（不加的话效果够不够？）

- [ ] 检索效果有评测吗？（召回率多少？）

### 上下文组装

- [ ] Prompt结构清晰吗？（系统指令/参考资料/用户问题）

- [ ] 有明确的"只基于参考资料回答"的指令吗？

- [ ] 检索内容编号和标来源了吗？

- [ ] 最相关的放前面了吗？

- [ ] Token长度控制好了吗？（不超过窗口的1/3）

### 生成层

- [ ] 温度参数设了多少？（跟场景匹配吗？）

- [ ] 幻觉控制做了几层？（指令/置信度/校验/引用）

- [ ] 生成效果有评测吗？（要点覆盖率/幻觉率/违规率）

### 优化迭代

- [ ] 三层失败模型用了吗？（分类/检索/生成）

- [ ] 归因分析做了吗？（哪类问题最多？）

- [ ] 优先级排了吗？（影响面×修复难度）

- [ ] 一次只改一个变量吗？

- [ ] 每次优化都有数据验证吗？

***

## 最后一句话

**好的RAG系统，不是技术最复杂的，而是每一层都刚刚好的。**

不要一开始就堆最复杂的技术——GraphRAG、多模态、Agent……
先把基础做好：知识库质量高、切片合理、检索参数调优、Prompt写好。

基础打牢了，再考虑高级玩法。
