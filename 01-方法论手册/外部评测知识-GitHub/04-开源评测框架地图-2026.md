# 04 · 开源评测框架地图（2026）

> 来源：DeepEval《Top 5 LLM Evaluation Frameworks in 2026》、各框架官方文档（GitHub / 官网）
> 定位：**先懂方法论，工具只是载体**——本文档只记"什么活该用什么工具"，不背 API

---

## 一、主流框架分工速览

| 框架 | 强项 | 形态 | 与我项目的关系 |
| --- | --- | --- | --- |
| **DeepEval** | 最全面：RAG、Agent 轨迹、多轮、合成数据、Pytest、CI/CD | Python，`pip install`，测试即代码 | Agent 三层指标（01 篇）的来源；未来给穿搭 Agent 化时首选 |
| **Promptfoo** | 配置驱动、红队/注入测试、多裁判投票、LLM-as-Judge 模板最全 | YAML + CLI，无需写代码 | 裁判 prompt 快速 A/B、pairwise 比较最顺手 |
| **Ragas** | RAG 垂类事实标准：faithfulness、context precision/recall、answer relevancy | Python 库 | 客服 RAG 7 维可与它的指标名对齐（faithfulness=忠实度） |
| **LangFuse / Phoenix（Arize）** | 可观测性 + 评测一体：trace、span、线上评分 | 自托管/云服务 | 对应"线上监控"这块我还缺的拼图 |
| **Braintrust / LangSmith** | 商业平台：数据集管理、实验对比、prompt 版本 | SaaS | 了解即可，小团队成本偏高 |

DeepEval 自己的结论（2026 评测）：**通用场景 DeepEval 最完整；专项需求选专才**——红队选 Promptfoo、只评 RAG 选 Ragas、要可观测选 LangFuse/Phoenix。

## 二、这些工具的共同骨架（记住骨架比记工具重要）

换任何框架，内部都是同一条流水线：

```
Dataset（评测集） → SUT（被测系统） → Metrics/Judge（指标与裁判）
       → Results（分数+证据） → CI Gate（门禁） → Trace（可追溯）
```

对照我的项目：505 用例 = Dataset；Dify 客服 = SUT；规则预检+v4.4 裁判 = Metrics；185 条回归集 = CI Gate；保留原始回复文本支持复评 = Trace。**我手工跑过的东西，正是这些框架自动化的对象**——这句话。

## 三、RAG 指标名对照表（客服项目 ↔ Ragas 行业词）

| 我项目叫法 | Ragas 行业叫法 | 一句话 |
| --- | --- | --- |
| 忠实度 | **Faithfulness** | 答案能否在检索上下文找到依据（防幻觉） |
| 答案相关性 | Answer Relevancy | 答案是否对准问题（防答非所问） |
| —（未单列） | Context Precision | 检索回来的内容里有用信息排得靠不靠前 |
| —（未单列） | Context Recall | 该召回的关键信息漏没漏 |
| 拒答/转人工 | Fallback / Refusal | 未命中知识库时的受控拒答 |

后两个是我客服项目可以补讲的行业词汇：我做的是系统级评测，Ragas 把检索质量单独量化了。

## 四、Agent 评测选型（穿搭项目未来落地建议）

- 若穿搭导购演进为多步 Agent：DeepEval 的 TaskCompletion + ToolCorrectness + StepEfficiency 三件套直接可用；
- 裁判实验：Promptfoo 的双序/多裁判配置能省手写脚本；
- 线上灰度：LangFuse 类工具做 trace 采样 + 自动打分，补上"评测只在离线做"的短板。
