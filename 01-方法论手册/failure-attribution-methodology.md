# 失败归因分析方法论 · 操作手册

> 生成日期：2026.10.06
> 来源：电商客服RAG评测项目 + AI穿搭导购项目（多轮归因分析实践提炼）
> 定位：找到问题的根因——从"知道错了"到"知道为什么错"

---

## 为什么归因分析很重要？

很多人做AI产品，是这样迭代的：
- "效果不好 → 改改Prompt → 再测 → 好像好一点了 → 继续改"

这叫"瞎试"——你不知道为什么错，也不知道为什么改了之后变好。全凭感觉。

**归因分析就是——搞清楚"为什么错"。**

> 知道了为什么错，你才能针对性地优化。
> 不知道为什么错，你就是在瞎碰运气。

**归因的价值**：
- 找到杠杆点——优化哪类问题，收益最大
- 避免瞎试——把精力花在真正有用的地方
- 深入理解系统——越归因，你对系统的理解越深
- 积累经验——下次遇到类似问题，很快就能定位

---

## 一、归因分析全景

### 1.1 什么是归因？

**归因 = 给失败分类 + 找根因**

- 每条失败用例，是什么原因导致的？
- 哪类原因最多？
- 最核心的问题是什么？
- 该先解决哪个？

**归因分析的产出**：
- 各类失败的数量和占比
- 优先级排序（先解决什么，后解决什么）
- 具体的优化建议

---

### 1.2 归因分析的完整流程

```
1. 收集失败用例
       ↓
2. 设计分类体系（根因有哪几类？）
       ↓
3. 逐条标注（每条失败是什么原因？）
       ↓
4. 统计汇总（各类占比多少？）
       ↓
5. 深度分析（为什么这类问题最多？根因是什么？）
       ↓
6. 排优先级（影响面 × 修复难度）
       ↓
7. 产出建议（具体怎么做？）
```

---

### 1.3 归因的两个层次

| 层次 | 回答什么问题 | 例子 |
|------|-------------|------|
| **表层归因** | 哪一类问题？ | 路由错误、检索不准、幻觉…… |
| **深层归因** | 为什么会有这类问题？根因是什么？ | 分类器训练数据不够？分类Prompt写得不好？类别定义不清晰？ |

**很多人的归因只做到第一层——"路由错了"。**
但这还不够——你知道是路由错了，但为什么路由会错？不知道。

**好的归因要挖到第二层——找到根因，才能对症下药。**

---

## 二、第一步：收集失败用例

### 2.1 失败用例从哪来？

| 来源 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **评测失败** | 跑评测集，没通过的 | 系统、全面、可量化 | 需要先有评测体系 |
| **用户反馈** | 用户投诉、差评、客服记录 | 真实、代表真实痛点 | 零散、有抽样偏差 |
| **线上日志** | 错误日志、异常指标 | 全量、覆盖所有用户 | 只能发现"有问题"，不知道"为什么" |
| **人工抽检** | 人工随机抽查看 | 能发现评测没覆盖的问题 | 慢、贵、样本少 |
| **Bad Case库** | 历史积累的问题案例 | 有积累、可追踪 | 需要持续维护 |

**最佳实践：多渠道收集，然后统一归因分析。**

---

### 2.2 失败用例要记录什么信息？

| 字段 | 说明 | 为什么重要 |
|------|------|-----------|
| **输入** | 用户问了什么/做了什么 | 知道触发条件 |
| **实际输出** | 系统返回了什么 | 知道错成什么样了 |
| **预期输出** | 正确的应该是什么 | 知道差距在哪 |
| **失败类型** | 属于哪类失败（表层归因） | 分类统计用 |
| **根因** | 为什么会错（深层归因） | 指导优化 |
| **严重程度** | 严重/一般/轻微 | 排优先级 |
| **来源** | 从哪发现的 | 知道数据可信度 |
| **发生频率** | 出现了多少次 | 估算影响面 |

---

### 2.3 多少条失败用例够归因？

| 数量 | 能做什么 |
|------|---------|
| < 10条 | 只能做定性分析，不够统计 |
| 10-30条 | 可以做初步归因，找大致方向 |
| 30-100条 | 比较可靠的归因，能看到明显的模式 |
| 100条+ | 非常可靠的归因，可以做精细的统计分析 |

**经验**：至少30条起步，才能看到比较清晰的模式。
如果失败用例太少——说明你的系统已经挺不错了，或者你的评测集太简单。

---

## 三、第二步：设计分类体系

### 3.1 分类体系的设计原则

**MECE原则**：
- **M**utually **E**xclusive —— 相互独立（一条用例只能归到一类）
- **C**ollectively **E**xhaustive —— 完全穷尽（所有用例都能找到对应的类别）

**设计分类体系的坑**：

| 坑 | 问题 | 怎么避免 |
|----|------|---------|
| 类别太少 | 太粗，不知道具体问题在哪 | 逐步细化，先粗后细 |
| 类别太多 | 太细，统计不起来，每类都没几条 | 控制在5-10类，归并相似的 |
| 类别重叠 | 一条用例可以归到多类，不知道归哪个 | 明确分类标准，按"最主要原因"归 |
| "其他"类太多 | 什么都往"其他"里塞，等于没分类 | "其他"占比超过10%，就拆开看看 |

---

### 3.2 怎么设计分类体系？

#### 方法1：按技术栈分层（推荐，最常用）

按系统的技术架构来分——每一层对应一类失败。

**例子：RAG系统的三层失败模型**

```
用户提问 → 分类 → 检索 → 生成 → 回答
            ↓      ↓      ↓
         L1失败  L2失败  L3失败
```

| 层级 | 失败类型 | 说明 |
|------|---------|------|
| **L1 分类层** | 意图分类错误 | 分到了错误的业务分支 |
| **L2 检索层** | 检索失败 / 检索不准 | 没找到 / 找错了 |
| **L3 生成层** | 幻觉 / 表述问题 / 格式错误 | 找到了但生成不对 |

**优点**：
- 跟技术架构对应，出了问题知道去哪一层找
- 每层的优化方法不一样，归因之后直接知道怎么优化
- 逻辑清晰，不容易混淆

**适用场景**：有明确技术分层的系统（RAG、Agent、流水线式的AI系统）

---

#### 方法2：按失败性质分类

按"错的是什么性质的问题"来分。

| 类型 | 说明 |
|------|------|
| **准确性问题** | 内容不对、事实错误、幻觉 |
| **完整性问题** | 缺信息、漏要点、回答不完整 |
| **相关性问题** | 答非所问、跑题 |
| **格式问题** | 格式不对、结构混乱 |
| **安全性问题** | 违禁内容、隐私泄露、偏见 |
| **体验问题** | 太慢、太啰嗦、语气不对 |

**优点**：跟技术架构无关，适用于各种AI产品
**缺点**：归因之后还要再想——这是哪一层的问题？该怎么优化？

---

#### 方法3：按严重程度分类

| 级别 | 说明 | 处理方式 |
|------|------|---------|
| **致命** | 完全不可用、安全问题、合规红线 | 最高优先级，立刻修 |
| **严重** | 核心功能出错、用户明显感知 | 高优先级，尽快修 |
| **一般** | 有瑕疵但不影响使用 | 正常排期 |
| **轻微** | 很小的问题，大部分用户注意不到 | 有空再修，或者不修 |

这个通常跟其他分类方法结合用——先分类型，再标严重程度。

---

### 3.3 分类体系是迭代出来的

不要一上来就搞十几个分类——你想不全的。

**正确做法**：
1. 先拿20-30条失败用例，手动分类看看
2. 看看大概有几类原因，设计初始分类（3-5类起步）
3. 用更多用例验证，调整分类（合并、拆分、新增）
4. 最终稳定在5-10类比较合适

**分类体系会随着你对系统的理解加深而不断完善。**

---

## 四、第三步：逐条标注

### 4.1 怎么标注？

1. 拿一条失败用例
2. 看输入、看输出、看预期
3. 判断：这是什么原因导致的？
4. 标上分类标签
5. 如果有多层分类（比如L1/L2/L3 + 细分类型），都标上
6. 写下你的判断理由（可选，但推荐）

**标注时的常见疑问**：

**Q：一条用例可能有多个原因，归到哪一类？**
A：归到"最根本的原因"或者"最主要的原因"。或者你可以标多个标签——但统计的时候要小心重复计数。

**Q：判断不准怎么办？**
A：先归到"其他"或者"待确认"，等积累多了一起看。或者找第二个人一起判断。

---

### 4.2 标注一致性检验

如果有多个人标注，或者你分多次标注——要检查**标注一致性**。

**怎么检查？**
- 两个人（或者两次）独立标注同一批用例
- 看一致率有多高
- 一致率高 → 分类定义清晰，标注可靠
- 一致率低 → 分类定义有问题，需要澄清

**一致率多少算合格？**
- 80%+ → 很好
- 70-80% → 还行，但有改进空间
- <70% → 分类体系有问题，需要重新设计

**为什么重要？**
- 如果标注不一致，统计出来的结果就不可信
- 这次你这么标，下次你那么标——数据就乱了
- 一致率低，说明分类定义本身就不清楚

---

### 4.3 标注的注意事项

1. **按事实标，不要猜**——有证据才下结论，不确定的标"待确认"
2. **标最根本的原因**——不是表面现象，是根因
3. **一致的标准**——同类型的问题，要归到同一类
4. **记录理由**——为什么这么标？写下来，方便后面复盘
5. **有疑问的单独放**——拿不准的别硬标，攒多了一起看

---

## 五、第四步：统计汇总

### 5.1 基本统计

标注完了，先算基本的统计：

| 统计项 | 说明 |
|--------|------|
| **总失败数** | 一共多少条失败用例 |
| **各类数量** | 每类失败有多少条 |
| **各类占比** | 每类占总失败的百分比 |
| **排序** | 按数量从多到少排 |

**输出形式**：
- 表格：类别、数量、占比，按占比排序
- 饼图/柱状图：可视化（可选）

---

### 5.2 怎么看统计结果？

#### 看分布：是集中还是分散？

| 分布类型 | 特征 | 意味着什么 |
|---------|------|-----------|
| **集中型** | 一类占比 > 50% | 有一个核心问题，解决了它就能提升一大截 |
| **分散型** | 每类占比都差不多，没有特别突出的 | 没有单一核心问题，需要一个个来 |
| **头部型** | 前两类占60-70%，后面逐渐减少 | 先解决前两个大头，剩下的慢慢来 |

**集中型的最划算**——找到那个最大的问题，集中火力搞定，效果最明显。
**分散型的最麻烦**——没有捷径，只能一个个来。

---

### 5.3 多维度交叉分析

除了单维度的统计，还可以做交叉分析——

| 交叉维度 | 能回答什么问题 |
|---------|--------------|
| 失败类型 × 业务分支 | 哪个分支的问题最多？哪类问题在哪个分支最突出？ |
| 失败类型 × 难度等级 | 是不是难题更容易出错？哪类问题在难题里最多？ |
| 失败类型 × 严重程度 | 致命的问题是哪类？一般的问题是哪类？ |
| 失败类型 × 时间 | 哪类问题在减少？哪类在增加？ |

**交叉分析能发现更细的模式——帮助你更精准地定位问题。**

---

## 六、第五步：深度分析——找根因

### 6.1 为什么要深度分析？

知道"路由错误占70%"还不够——
- 为什么路由错误这么多？
- 是分类Prompt写得不好？
- 是训练数据不够？
- 是类别定义不清晰？
- 还是用户的问题本身就模糊？

**不同的根因，优化方法完全不一样。**
- 如果是Prompt的问题 → 改Prompt，成本低，见效快
- 如果是数据的问题 → 加数据，成本中等
- 如果是类别定义的问题 → 重新设计分类体系，成本高

**不找到根因，你可能在错误的方向上使劲。**

---

### 6.2 5Why分析法：连续问5个"为什么"

这是最经典的根因分析方法——遇到问题，连续问5个"为什么"，直到挖到根因。

**例子**：
```
问题：路由错误很多
为什么？→ 分类器分不准
为什么分不准？→ 边界场景容易搞混
为什么边界场景容易搞混？→ 两个类别的定义有重叠
为什么定义有重叠？→ 最开始设计分类的时候，没考虑清楚边界情况
为什么没考虑清楚？→ 设计分类的时候，是按业务部门分的，不是按用户意图分的
⇒ 根因：分类体系设计有问题，需要重新设计
```

**注意**：
- 不一定非要问5次——问到根因为止，可能3次，可能7次
- 每个"为什么"都要有事实依据，不能瞎猜
- 挖到可以行动的根因为止——再往下挖就没有意义了

---

### 6.3 钻进去细看：把同一类失败放在一起看

统计告诉你"哪类问题最多"，但要知道"为什么这类问题最多"，你得——
**把同一类的所有失败用例放在一起，一条一条细看。**

**看什么？**
1. **有没有共同的模式？**——是不是都是某种类型的输入容易错？
2. **有没有规律？**——错的方式是不是都一样？
3. **有没有子类型？**——这一类里面，是不是还可以再分成几小类？
4. **反例是什么？**——类似的输入，为什么有的对了有的错了？差别在哪？

**这是最费时间但也最有价值的一步——很多洞见都是这么看出来的。**

---

### 6.4 相关性分析：找杠杆维度

除了"哪类问题最多"，你还要知道——**哪个维度的提升，对整体效果的拉动最大？**

**怎么做**：
- 算各个维度跟总通过率的相关性系数
- 相关性越高，说明这个维度越"杠杆"——优化它，整体提升最大

**实战案例**：
```
信息完整性 → 与通过率相关性 r = 0.859 （最高）
路由准确率 → r = 0.82
意图准确率 → r = 0.75
幻觉率    → r = 0.6
```

**解读**：
- 信息完整性跟通过率最相关——提升信息完整性，对整体通过率的拉动最大
- 这就是**杠杆维度**——投入同样的精力，优化这个维度收益最大

**为什么有用？**
- 资源有限，你不可能什么都优化
- 找杠杆维度，就是找"投入产出比最高"的优化方向
- 把80%的精力，投入到20%收益最高的地方

---

### 6.5 常见的归因谬误

归因的时候，很容易犯这些错误——

#### 谬误1：把相关当因果

**表现**：A和B相关，就说A导致了B。

**例子**："冰淇淋销量上升的时候，溺水死亡人数也上升，所以冰淇淋导致溺水。"——其实是因为夏天到了，两者都上升，没有因果关系。

**怎么避免**：
- 相关不等于因果
- 要证明因果，需要更严格的证据（比如A/B测试）
- 想想有没有第三个因素同时影响A和B

---

#### 谬误2：单一归因

**表现**：复杂的问题，只找一个原因。

**例子**："效果不好就是因为Prompt写得不好。"——可能还有数据的问题、模型的问题、检索的问题……

**怎么避免**：
- 复杂问题通常有多个原因
- 找主要原因，但也要看到次要原因
- 不要用"就是因为XX"这种绝对化的说法

---

#### 谬误3：确认偏误

**表现**：先有结论，然后找证据支持自己的结论。忽略反面证据。

**例子**："我觉得是检索的问题"——然后只看检索出错的例子，不看检索对了但生成错了的例子。

**怎么避免**：
- 先看数据，再下结论——不要反过来
- 主动找反例——有没有不符合我结论的情况？
- 考虑其他可能的解释

---

#### 谬误4：归因而不解决

**表现**：归因分析做了一大堆，最后报告写得很漂亮，但什么也没改。

**例子**："70%是路由错误"——然后就没有然后了。

**怎么避免**：
- 归因的终点是"行动"——归因完了一定要有优化建议和优先级
- 归因报告最后必须有"建议动作"部分
- 不落地的归因，就是纸上谈兵

---

## 七、第六步：排优先级

### 7.1 优先级矩阵：影响面 × 修复难度

不是所有问题都要立刻修。怎么排优先级？

用**影响面 × 修复难度**的四象限矩阵：

```
          修复难度
    低 ←────────────→ 高
  ┌─────────┬─────────┐
高│  P0立即做 │  P2规划做 │
  │  影响大  │  影响大  │
影│  成本低  │  成本高  │
响├─────────┼─────────┤
面│  P1顺手做 │  P3再说  │
低│  影响小  │  影响小  │
  │  成本低  │  成本高  │
  └─────────┴─────────┘
```

| 象限 | 优先级 | 怎么做 |
|------|--------|--------|
| 影响大 × 成本低 | **P0** | 立刻做，投入产出比最高 |
| 影响小 × 成本低 | **P1** | 顺手做，反正成本不高 |
| 影响大 × 成本高 | **P2** | 规划一下，找合适的时机做 |
| 影响小 × 成本高 | **P3** | 算了，不值得做 |

---

### 7.2 "影响面"怎么估？

| 方法 | 说明 | 准确度 |
|------|------|--------|
| **失败占比** | 这类失败占总失败的百分比 | 高 |
| **用户影响** | 影响多少用户/多少使用场景 | 中 |
| **严重程度** | 出了这个问题，后果有多严重 | 中（主观） |
| **业务价值** | 修复了之后，对业务指标的提升有多大 | 中 |

**综合考虑，不是只看一个维度。**

---

### 7.3 "修复难度"怎么估？

| 因素 | 说明 |
|------|------|
| **改什么** | 改Prompt？改代码？改数据？改架构？ |
| **工作量** | 几小时？几天？几周？ |
| **风险** | 改了之后会不会引入新问题？ |
| **依赖** | 有没有依赖其他人/其他团队？ |
| **成本** | 要不要花钱？（比如加新的API、买新的服务） |

---

### 7.4 一个常见误区："哪里最差先修哪里"

很多人会说："这个分支通过率最低，只有60%，先修这个！"

**这是错的。**

为什么？
- 通过率最低，但它只有10条用例——就算全修好了，整体也提升不了多少
- 另一个分支通过率75%，但有100条用例，而且修复成本很低——修这个收益更大

**核心原则**：
> **不是看"哪里最差"，是看"修哪里收益最大"。**
>
> 最差的地方，如果影响面很小，修了也没什么用。
> 看起来不是最差的地方，如果影响面大、修复成本低，反而应该先修。

---

## 八、第七步：产出建议

### 8.1 归因报告的标准结构

```
1. 概述（本次分析了多少条失败用例、整体情况）
2. 分类统计（各类失败的数量和占比、排序）
3. 深度分析（每类问题的根因、典型案例、规律）
4. 杠杆分析（相关性分析、哪个维度最值得优化）
5. 优先级排序（P0/P1/P2/P3，各是什么）
6. 优化建议（每个优先级的问题，具体怎么优化）
7. 预期收益（优化之后，预计能提升多少）
8. 后续计划（什么时候做、谁来做、怎么验证）
```

---

### 8.2 优化建议怎么写？

**好的优化建议是具体的、可执行的、有预期的。**

| 不好的建议 | 好的建议 |
|-----------|---------|
| "优化分类器" | "优化分类Prompt，把边界场景的区分逻辑写得更明确，预计需要1天，预期边界场景准确率提升10个百分点" |
| "提升检索效果" | "增加Top K从3到5，同时调整相似度阈值从0.5到0.4，先跑评测看效果，预计半天" |
| "减少幻觉" | "在Prompt里加强'只基于参考资料回答'的指令，调低temperature从0.5到0.2，预计1小时" |

**每个建议都要回答**：
- 做什么？（具体动作）
- 为什么做？（对应哪类问题）
- 怎么做？（具体方法）
- 多久能做完？（工作量）
- 预期效果？（能提升多少）
- 怎么验证？（怎么知道有没有用）

---

### 8.3 预期收益怎么估？

不用特别精确，有个大概的估计就行：

| 方法 | 说明 |
|------|------|
| **按占比估** | 这类问题占X%，全修好的话，通过率能提升X% |
| **按历史经验估** | 上次优化类似的问题，提升了多少 |
| **按小样本实验估** | 先拿一小部分测一下，看看能提升多少，再放大 |
| **保守估计** | 打个折——比如理论上能提升10%，保守估5% |

**为什么要估预期收益？**
- 不估的话，你不知道值不值得做
- 有了预期，做完之后可以对比——是不是达到了预期？
- 没达到预期的话，可以再分析——为什么没达到？是哪里判断错了？

---

## 九、不同类型产品的归因框架

### 9.1 RAG/问答类产品

**三层失败模型**：
```
L1 分类层：意图分类错误
L2 检索层：检索不到 / 检索不准
L3 生成层：幻觉 / 表述问题 / 格式错误
```

**细分类型**：
- 分类错误：相似意图混淆、边界场景、新意图
- 检索错误：切片问题、Embedding问题、参数问题、知识库问题
- 生成错误：Prompt问题、模型问题、温度太高、上下文噪音

---

### 9.2 分类/判别类产品

**混淆矩阵**：

| | 预测为A | 预测为B | 预测为C |
|---|---------|---------|---------|
| **实际A** | ✓ 正确 | ✗ 错分为B | ✗ 错分为C |
| **实际B** | ✗ 错分为A | ✓ 正确 | ✗ 错分为C |
| **实际C** | ✗ 错分为A | ✗ 错分为B | ✓ 正确 |

**看什么？**
- 哪两类最容易混淆？（对角线外面的格子，哪个最多）
- 哪一类最容易被分错？（哪一行的错误最多）
- 哪一类最容易"吸"别的类？（哪一列的错误最多）

**为什么有用？**
- 找到最容易混淆的类别对，针对性优化
- 比如A和B总是搞混 → 就专门优化A和B的区分

---

### 9.3 生成/创意类产品

**质量维度归因**：
- 内容质量：相关性、准确性、完整性
- 表达质量：流畅度、自然度、风格一致性
- 结构质量：格式、逻辑、层次
- 安全质量：违禁、偏见、隐私

**这类产品的归因更难**——因为没有绝对的"对"和"错"，更多是"好"和"更好"。
需要用LLM Judge或者人工评测，从多个维度来评估。

---

### 9.4 Agent/工具调用类产品

**工具调用失败模型**：
```
用户意图 → 工具选择 → 参数提取 → 工具执行 → 结果整理
             ↓          ↓          ↓          ↓
          选错工具   参数错了   执行失败   结果理解错
```

| 失败类型 | 说明 | 优化方向 |
|---------|------|---------|
| 工具选错 | 选了不该选的工具 | 优化工具描述、优化选择逻辑 |
| 参数错 | 提取的参数不对 | 优化参数提取Prompt、加参数校验 |
| 执行失败 | 工具调用出错 | 加错误处理、加重试 |
| 结果理解错 | 拿到结果但理解错了 | 优化结果处理Prompt |

---

## 十、常见坑 & 避坑指南

### 坑1：归因只做表层，不深挖根因

**症状**："70%是路由错误"——然后就直接去优化路由了，但不知道为什么路由错。

**后果**：可能在错误的方向上使劲——以为是Prompt的问题，其实是分类体系设计的问题。

**避坑**：多问几个"为什么"。知道是什么类型的问题之后，还要往下挖——为什么这类问题这么多？根因是什么？

---

### 坑2：一次归完就完事了

**症状**：做了一次归因分析，出了份报告，然后就扔在那了。

**后果**：归因报告落灰，问题还是那些问题，没有改善。

**避坑**：归因的终点是行动。归因完了一定要有优化建议、有优先级、有跟进计划。而且归因是持续的——每次迭代都要做，看问题分布有没有变化。

---

### 坑3：把相关当因果

**症状**："A和B相关，所以A导致了B。"

**后果**：在错误的方向上优化，白费力气。

**避坑**：相关不等于因果。要证明因果，需要更严格的证据（比如A/B测试、干预实验）。想想有没有第三个因素同时影响两者。

---

### 坑4：分类体系太粗或太细

**症状**：要么只有3类，什么都往里塞，看不出细节；要么20多类，每类没几条，统计不起来。

**后果**：太粗 → 找不到具体问题；太细 → 看不出模式。

**避坑**：5-10类比较合适。先粗分，有需要再细分。MECE原则——相互独立，完全穷尽。

---

### 坑5：归因的人自己有偏见

**症状**："我觉得是检索的问题"——然后只看检索出错的例子，不看其他的。

**后果**：确认偏误——只看支持自己结论的证据，忽略反面证据。

**避坑**：先看数据，再下结论。主动找反例。考虑多种可能的解释。可以两个人独立归因，然后对比结果。

---

## 十二、下一个项目复用检查清单

做下一个项目的时候，照着这个清单做归因分析：

### 准备工作
- [ ] 有评测体系吗？（能产出失败用例）
- [ ] 失败用例有多少条？（至少30条起步）
- [ ] 每条失败用例记录完整吗？（输入/输出/预期/来源）

### 归因流程
- [ ] 设计了分类体系吗？（MECE原则，5-10类）
- [ ] 分类体系是按什么分的？（技术栈/失败性质/严重程度）
- [ ] 逐条标注了吗？（每条都有分类标签）
- [ ] 标注一致性检验做了吗？（>80%才算可靠）
- [ ] 统计汇总了吗？（各类数量、占比、排序）
- [ ] 深度分析了吗？（根因分析、模式挖掘）
- [ ] 5Why分析用了吗？（挖到可以行动的根因）
- [ ] 相关性分析做了吗？（找杠杆维度）
- [ ] 优先级排了吗？（影响面×修复难度矩阵）
- [ ] 优化建议写了吗？（具体怎么做、工作量、预期收益、验证方法）

### 归因质量自查
- [ ] 是表层归因还是深层归因？（有没有挖到根因）
- [ ] 有没有把相关当因果？（警惕）
- [ ] 有没有确认偏误？（主动找反例了吗）
- [ ] 分类体系合适吗？（不太粗也不太细）
- [ ] 归因能指导行动吗？（还是只是"看起来很专业"）
- [ ] 验证归因了吗？（干预验证/找反例/交叉验证）

### 常见坑自查
- [ ] 只做表层归因，不深挖根因吗？
- [ ] 一次归完就完事了吗？（还是持续迭代）
- [ ] 哪里最差先修哪里吗？（还是看收益最大）
- [ ] 凭感觉归因吗？（还是用数据说话）
- [ ] 归因完了有行动吗？（还是只出报告）

---

## 最后一句话

**归因分析不是目的，行动才是。**

知道为什么错了，但什么也不改——等于白做。

好的归因分析，是能直接指导行动的——
- 先做什么？
- 为什么先做它？
- 怎么做？
- 做完了预期有什么结果？

把归因变成行动，把行动变成结果。
这才是归因的真正价值。
