# AI产品设计方法论 · 操作手册

> 生成日期：2026.10.06
> 来源：AI穿搭导购 + 电商客服RAG（97份文档提炼 + 产品经验沉淀）
> 定位：AI产品设计的核心原则——跟传统产品设计不一样的地方

---

## 为什么AI产品设计不一样？

传统软件是**确定性的**——你点一下按钮，就会发生确定的事。产品经理的工作是"定义功能"。

AI产品是**概率性的**——同样的输入，可能输出不一样的结果；有时候对，有时候错；甚至会"胡说八道"。产品经理的工作变成了"定义能力边界"。

> **传统产品经理 = 功能定义者**
> **AI产品经理 = 智能架构师**

你要设计的不只是"有什么功能"，更是——
- AI的边界在哪里？什么让它做，什么不让它做？
- 出错了怎么办？怎么兜底？
- 用户等不及了怎么办？怎么管理预期？
- 怎么让用户信任AI？怎么减少"黑盒焦虑"？

这些都是AI产品特有的设计问题。传统产品设计的方法论，解决不了这些问题。

## 一、场景选择：什么样的场景适合用AI？

### 1.1 场景识别三要素

不是什么场景都适合用AI。好的AI场景，三个要素都要满足：

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  痛点强度高  │  │  数据可得性  │  │  容错空间   │
│  （值得做）  │  │  （可以做）  │  │  （敢上线） │
└─────────────┘  └─────────────┘  └─────────────┘
        ↘               ↓               ↙
              三者都满足 → 适合AI
```

| 要素 | 说明 | 判断标准 |
|------|------|---------|
| **痛点强度高** | 这个问题值得解决 | 重复性高 / 人工成本高 / 规则复杂 / 用户自己搞不定 |
| **数据可得性** | AI有东西可学 | 有知识库 / 有历史数据 / 有标注数据 |
| **容错空间** | 错了也没关系 | 有兜底机制 / 错了后果不严重 / 用户能自己判断 |

**反例（不适合AI的场景）**：
- 容错空间为零的场景（手术、飞行控制、判决）——错了就是人命关天
- 没有数据的场景——巧妇难为无米之炊
- 规则简单、用规则引擎就能搞定的——杀鸡焉用牛刀

---

### 1.2 ROI判断：值不值得用AI？

就算场景适合，还要算一笔账——**用AI的成本，跟省下来的钱比，值不值？**

| 成本 | 收益 |
|------|------|
| API调用费用（Token钱） | 人力成本节约 |
| 开发和维护成本 | 效率提升（同样的人做更多事） |
| 质量下降的损失（幻觉、错误） | 转化率提升 / 收入增加 |
| 用户体验下降的风险 | 用户满意度提升 / 留存增加 |

**简单的判断方法**：
- 如果AI能替代**80%的人工工作量**，成本只有人工的**1/10**——那肯定值
- 如果AI只能替代**20%**，还需要**一堆人做审核和兜底**——那就要算算了

**实战案例**：
> 智能客服为什么是AI落地最成熟的场景？
> - 痛点强：用户问题重复度高（70%以上是重复问题），人工客服成本高
> - 有数据：有大量历史对话和知识库
> - 有兜底：答不上来可以转人工
> - ROI明确：AI接走70%的简单问题，人工成本直接降70%
>
> 三个要素全满足，ROI也清楚——所以智能客服是每个公司做AI的首选。

---

### 1.3 "锤子找钉子"陷阱

> **最常见的错误：为了用AI而用AI。**

表现：
- "我们要做AI+XX"
- "大模型这么火，我们也得搞一个"
- "竞品都有了，我们也得有"

结果：
- 做了一个"有AI"的产品，但用户并不觉得更好用
- 花了很多钱，效果一般，最后沦为摆设

**怎么避免？**
- 先问：用户的痛点是什么？——别先想着"我要用AI"
- 再问：不用AI能不能解决？——能用规则解决的，就不用AI
- 最后问：用了AI之后，体验能提升多少？——值不值那个成本

**核心原则**：
> **不是"AI能做什么，我们就做什么"，是"用户需要什么，我们就用什么方法解决"。**
>
> AI只是工具，不是目的。

## 二、混合架构原则：规则优先，AI兜底

### 2.1 为什么要混合架构？

很多人做AI产品，总想"全用大模型"——什么都让大模型生成，觉得这样才"AI Native"。

但实际上，全用大模型有很多问题：
- **不稳定**：有时候对，有时候错
- **贵**：每次调用都要钱
- **慢**：生成需要时间，用户等不及
- **不可控**：你不知道它会输出什么

**混合架构就是——能用规则解决的，就用规则；规则搞不定的，再用AI。**

```
┌──────────────────────────────────┐
│            用户输入              │
└──────────────┬───────────────────┘
               ↓
        ┌──────▼──────┐
        │  规则引擎    │  ← 能规则化的先走规则
        │ （快/准/便宜）│
        └──────┬──────┘
               ↓ 规则搞不定？
        ┌──────▼──────┐
        │  大模型生成  │  ← 需要灵活性和理解力的用AI
        │ （灵活/智能） │
        └──────┬──────┘
               ↓
        ┌──────▼──────┐
        │  规则校验    │  ← AI输出之后，用规则兜底检查
        │  （防离谱）  │
        └──────┬──────┘
               ↓
        ┌──────▼──────┐
        │  输出给用户   │
        └─────────────┘
```

**三层混合架构**：
1. **前置规则**：能规则化的，先走规则，不碰大模型
2. **中间AI**：需要灵活性的，用大模型生成
3. **后置校验**：AI输出之后，用规则检查一遍，防止离谱

---

### 2.2 什么该用规则？什么该用AI？

| 适合用规则的 | 适合用AI的 |
|------------|-----------|
| 有明确对错的 | 没有标准答案的 |
| 重复出现的 | 多样化、个性化的 |
| 容错空间低的 | 容错空间高的 |
| 逻辑简单直接的 | 需要理解和推理的 |
| 高频调用、成本敏感的 | 调用量不大、但效果重要的 |

**简单判断方法**：
> 如果你能用"如果…那么…"写清楚——就用规则。
> 如果你说不清，但你知道"好的是什么样的"——就用AI。

---

### 2.3 实战案例：穿搭项目的混合架构

**用规则的（确定性算法）**：
- 颜色搭配规则（硬约束4条）
- 温度适配规则（什么温度穿什么厚度）
- 体型扬长避短规则（梨形/苹果型/H型怎么穿）
- 色名表和颜色计算（105条）
- 量感计算和匹配
- 硬约束校验（冲突的单品不能搭在一起）

**用AI的（大模型生成）**：
- 造型师笔记（个性化的搭配建议和理由）
- 风格理解和推荐
- 购物指南（选购建议）
- 场景适配（不同场合怎么穿）

**为什么这么分？**
- 搭配规则是客观的——红色和绿色不能乱搭，就是不能乱搭。用规则，100%准确，零成本。
- 风格建议是主观的——怎么说好听、怎么说有道理，AI比规则擅长多了。

**后置校验**：
- AI生成的搭配方案，要用规则层校验一遍——有没有违反硬约束？颜色冲不冲突？温度合不合适？
- 通过了，才输出给用户
- 没通过，打回去重新生成，或者用规则选一个合格的

---

### 2.4 混合架构的好处

| 好处 | 说明 |
|------|------|
| **更稳定** | 核心功能靠规则，稳定可靠 |
| **更便宜** | 规则不花钱，AI只在需要的时候用 |
| **更快** | 规则毫秒级返回，不用等大模型生成 |
| **更可控** | 规则说了算的地方，不会出离谱的错 |
| **效果更好** | AI负责它擅长的，效果上限高 |
| **可解释性强** | 规则部分能说清"为什么"，AI部分负责"说得好" |

**一句话总结**：
> **规则保下限，AI冲上限。**
>
> 规则保证产品不会太差，AI让产品可以很好。

## 三、容错设计：AI会犯错，产品要兜底

### 3.1 容错不是"bug"，是AI产品的"常态"

传统软件的bug是"不正常的"——修好了就不会再出现。

但AI产品的"犯错"是**正常的**——因为它是概率模型，总会有出错的时候。你不可能把错误降到零，就像你不可能让天气预报100%准确一样。

**所以AI产品设计的第一原则就是——假设AI会犯错，然后设计兜底机制。**

---

### 3.2 容错设计的6种武器

| 武器 | 说明 | 适用场景 |
|------|------|---------|
| **1. 置信度判断** | AI自己说"我不确定" | 有置信度输出的场景 |
| **2. 引用溯源** | 告诉用户答案从哪来的 | RAG类产品 |
| **3. 兜底话术** | 答不上来就直说，别硬答 | 问答类产品 |
| **4. 人工兜底** | 搞不定就转人工 | 客服、高价值场景 |
| **5. 多方案对比** | 给多个选项，用户自己选 | 推荐类、创意类 |
| **6. 可编辑/可修正** | 用户可以改AI的输出 | 写作、生成类 |

---

#### 武器1：置信度判断

**原理**：让AI不仅输出答案，还输出"我对这个答案有多大把握"。把握低的时候，就走兜底。

**怎么实现？**
- 检索置信度：检索分数低于阈值 → 没找到相关内容
- 生成置信度：对数概率、熵值等（有些模型支持）
- 规则判断：答案里有没有关键信息？有没有自相矛盾？

**实战案例（客服项目）**：
> 检索分数低于0.5的，直接走"没找到相关内容，帮您转人工"的兜底话术。
>
> 宁可少说，也不能说错——因为说错了比不说更糟糕，用户会觉得你在忽悠他。

---

#### 武器2：引用溯源

**原理**：告诉用户"答案是从哪来的"，用户可以自己去验证。

**为什么有用？**
- 增加可信度——用户知道你不是瞎编的
- 出错了用户也能理解——"哦，原文就是这么写的"
- 方便深入了解——感兴趣的用户可以去看原文

**适用场景**：
- RAG类产品（知识库问答、客服）
- 法律、金融、医疗等高合规场景
- 需要用户自己做判断的场景

---

#### 武器3：兜底话术

**原理**：答不上来的时候，大方承认"我不知道"，而不是硬编。

**好的兜底话术**：
- 诚实："这个问题我暂时回答不了"
- 有帮助："我帮您转人工客服" / "您可以看看XX文档"
- 不丢人：大方承认，不要找借口

**坏的兜底话术**：
- 含糊其辞："这个问题比较复杂……"（然后开始瞎扯）
- 甩锅："因为数据不足，所以……"
- 阴阳怪气："您可以换一种问法试试"（暗示用户不会问）

---

#### 武器4：人工兜底

**原理**：AI搞不定的，交给人来。

**什么时候转人工？**
- 置信度低的时候
- 用户明确要求人工的时候
- 高风险场景（投诉、退款、纠纷）
- 用户多次重复同一个问题（说明AI没解决）

**设计要点**：
- 转人工要顺畅——别让用户重复说一遍问题
- 要有过渡："这个问题我帮您转接人工客服，他会为您详细解答"
- 记录上下文——把之前的对话一起转给人工

---

#### 武器5：多方案对比

**原理**：不给"唯一正确答案"，而是给几个选项，让用户自己选。

**为什么好？**
- 降低用户的"被代表感"——不是AI替我做决定，是我自己选的
- 容错空间变大——这个不好还有那个
- 增加参与感——用户有选择权

**适用场景**：
- 推荐类（穿搭、音乐、电影）
- 创意类（写作、设计）
- 没有唯一正确答案的场景

---

#### 武器6：可编辑/可修正

**原理**：AI生成的内容，用户可以改。改了之后，AI还能跟着调整。

**为什么好？**
- 容错——AI错了用户可以改
- 个性化——用户可以调成自己喜欢的样子
- 数据飞轮——用户修改的内容，可以用来优化AI

---

### 3.3 容错的"度"：什么时候该保守，什么时候可以激进？

| 场景类型 | 容错策略 | 例子 |
|---------|---------|------|
| **高风险** | 零容错，必须人工 | 医疗诊断、法律判决、金融交易 |
| **中风险** | 低容错，多重兜底 | 客服问答、信息查询 |
| **低风险** | 高容错，鼓励探索 | 创意生成、娱乐推荐、聊天 |

**核心判断标准**：
> **错了的后果有多严重？**
>
> 后果越严重，容错设计就要越保守。
> 后果不严重，就可以激进一点，让AI多发挥。

## 四、预期管理：等待体验与用户心理

### 4.1 为什么AI产品的"等待"特别难搞？

传统软件是"即时反馈"——你点一下，结果立刻出来。

AI产品不一样——生成需要时间，几秒到几十秒不等。用户等不及了，就会走。

**数据说话**：
- 8-20秒是弃用关键窗（20-35%流失）
- 20-60秒，用户大概率切走
- 60秒以上，必须按后台任务设计（完成通知、可切走），全屏spinner是反模式

**更要命的是**：
> **等60秒拿到平庸结果的挫败感，等于即时拿到错误结果的10倍。**
>
> "Slow and smart is only acceptable if it's right"——慢，就必须对。
> 又慢又错，用户会疯掉。

---

### 4.2 等待体验设计的4个层次

| 层次 | 做法 | 用户感受 |
|------|------|---------|
| **L1 最差** | 全屏spinner，什么都不显示 | "卡住了吗？还要多久？" |
| **L2 基本** | 显示"加载中"+ 进度条 | "知道在跑了，但还是着急" |
| **L3 好的** | 显示正在做什么（思考步骤）+ 阶段性结果 | "知道在做什么，感觉很快" |
| **L4 最好** | 分层交付——核心内容先到，二级内容后到 | "马上就有结果了，先看起来" |

---

### 4.3 分层交付：AI产品的预期管理利器

**什么是分层交付？**
> 核心方案先到（用户预期＝快），二级内容按需出现（预期＝准）。分开供给，各得其所。

**为什么好用？**
- 第一屏时间大大缩短——用户很快就能看到东西，不会觉得慢
- 二级内容慢慢加载——用户看核心内容的时候，后台在生成二级内容
- 预期管理到位——用户知道"主要的已经出来了，更多内容还在生成"

**实战案例（穿搭项目）**：
- 核心穿搭方案先出来（上衣、下装、鞋、搭配要点）——大概10-15秒
- 造型师笔记、购物指南这些二级内容，后面慢慢生成——用户看方案的时候，后台在生成
- 用户点击"生成购物指南"的时候，再生成更详细的内容

**设计要点**：
- 什么是"核心"？——用户最关心的、决定"好不好"的
- 什么是"二级"？——加分项、有了更好、没有也行的
- 核心一定要快，二级可以慢
- 二级内容的加载，要有明确的状态提示（生成中…），别让用户以为坏了

---

### 4.4 等待分区管理：不同时长不同策略

| 等待时长 | 用户心理 | 设计策略 |
|---------|---------|---------|
| **< 0.1秒** | 即时感 | 不需要任何反馈，直接出结果 |
| **0.1-1秒** | 很快 | 轻微的状态变化就行（比如按钮变色） |
| **1-8秒** | 等一下，可以接受 | 显示进度/状态，让用户知道在跑 |
| **8-20秒** | 有点久了，开始不耐烦 | 显示具体进展、告诉用户还要多久、给点东西看 |
| **20-60秒** | 等不及了，想切走 | 必须有明确进度 + 可以后台运行 + 切回来还能继续 |
| **> 60秒** | 肯定会切走 | 后台任务模式 + 完成通知 + 用户可以先做别的事 |

**核心洞察**：
> **缩短"试错回路的单位时长"，比缩短总时长更值。**
>
> 用户不怕等，怕的是"不知道还要等多久"和"等了半天结果还不行"。
> 快速知道"行还是不行"，比"等很久才知道行不行"好得多。

---

### 4.5 行为设计学：让等待"感觉"更快

有些时候，你没法真的变快，但你可以让用户**感觉**更快。

| 方法 | 原理 | 例子 |
|------|------|------|
| **显示进度** | 有进度的等待，感觉更快 | 百分比、步骤数、进度条 |
| **给点东西看** | 有东西看，就不会觉得慢 | 先显示骨架屏、先出一部分内容 |
| **告诉用户在做什么** | 知道"在做事"，就不会急 | "正在分析你的体型…""正在生成搭配方案…" |
| **让用户参与** | 有事做，时间就快 | 让用户选风格、调参数 |
| **乐观更新** | 先显示结果，后台再同步 | 点赞、收藏，先变样式，后台再存 |

**注意**：这些是"锦上添花"——首先你得真的不慢。如果本身就很慢，这些技巧没用，反而会让用户觉得你在"演"。

## 五、可解释性：消除黑盒焦虑

### 5.1 什么是"黑盒焦虑"？

用户用AI产品的时候，经常会有这种感觉：
- "它为什么给我推荐这个？"
- "这个答案对吗？靠谱吗？"
- "它是怎么想的？"

这就是**黑盒焦虑**——用户不知道AI是怎么得出结论的，所以不信任它。

**传统产品没有这个问题**——你搜一下"北京天气"，出来的结果你知道是从天气API来的，不会怀疑。

但AI不一样——它"思考"的过程是不透明的。用户不知道它是怎么想的，就不敢信。

---

### 5.2 怎么提升可解释性？

| 方法 | 说明 | 适用场景 |
|------|------|---------|
| **引用溯源** | 答案是从哪篇文档来的 | RAG类产品 |
| **推理链展示** | 把AI的"思考过程"显示出来 | 推理类、Agent类 |
| **置信度显示** | 我对这个答案有多大把握 | 所有场景 |
| **给出理由** | 为什么推荐这个、为什么这么判断 | 推荐类、决策类 |
| **可对比** | 给多个选项，差异在哪里 | 推荐类 |

---

#### 引用溯源

最简单也最有效的可解释性设计。

**怎么做**：
- 每个回答后面，标出来源："根据《退款政策》第3条"
- 可以点击跳转到原文
- 多个来源的话，分别标注

**效果**：
- 可信度大大提升——用户知道你不是瞎编的
- 错了也能理解——"哦，原文就是这么写的"
- 方便深入了解

---

#### 推理链展示

把AI的"思考过程"显示出来——就像一个人在解题，把步骤写出来。

**为什么好？**
- 用户能看到"它是怎么想的"
- 就算结果不对，用户也知道哪里错了
- 增加透明度和信任感

**注意**：
- 不是把所有思考都显示出来——太啰嗦了，用户不想看
- 提炼关键步骤，简洁明了
- 可以做成"展开查看详情"——默认不显示，想了解的用户自己点开看

---

### 5.3 可解释性的"度"

不是越多越好——太多信息反而会让用户困惑。

| 用户类型 | 需要的可解释性 |
|---------|--------------|
| 普通用户 | 很少——能用、结果对，就行 |
| 专业用户 | 中等——想知道为什么，自己判断对不对 |
| 管理员/运营 | 很多——要知道问题出在哪，怎么优化 |

**设计原则**：
- 默认只显示最关键的信息
- 想了解更多的用户，可以深入看
- 不要把所有人都当成专家

---

## 六、人机协作：AI做事，人把关

### 6.1 人机回环（Human-in-the-loop）

**什么是人机回环？**
> AI做大部分工作，人在关键节点把关。

不是AI全做，也不是人全做，是**人机协作**。

```
AI处理（快速、批量、低成本）
    ↓
关键节点 → 人工审核/确认
    ↓
AI继续处理
```

**为什么需要人？**
- AI会犯错——尤其是边界情况、复杂情况
- 有些事情AI做不了——需要人的判断力、同理心、创造力
- 有些责任AI担不起——需要人来拍板

---

### 6.2 什么时候需要人介入？

| 场景类型 | 例子 | 为什么要人 |
|---------|------|-----------|
| **高风险操作** | 转账、删除数据、合同签署 | 错了后果太严重 |
| **高合规场景** | 医疗建议、法律意见、金融投资 | 合规要求必须有人把关 |
| **低置信度** | AI自己都说"不确定" | 没把握的别瞎来 |
| **首次出现** | 新的问题类型、之前没见过的 | AI没学过，可能处理不好 |
| **用户要求** | 用户明确说"我要找人工" | 尊重用户选择 |
| **投诉/纠纷** | 用户不满意、有情绪 | 需要人的同理心和沟通能力 |

---

### 6.3 人机协作的三种模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **AI前置，人兜底** | AI先处理，搞不定的转人工 | 客服、问答（大多数场景） |
| **人前置，AI辅助** | 人先做判断，AI帮忙查找信息、生成草稿 | 专业场景（医生、律师、设计师） |
| **并行协作** | AI生成多个方案，人选一个或者修改 | 创意、设计、推荐 |

**没有最好的模式，只有最适合的模式。**
看你的产品场景、用户群体、容错空间来选。

---

### 6.4 让人有效介入的设计要点

1. **上下文完整**：人介入的时候，要能看到之前的完整对话/历史，别让用户重复说一遍
2. **无缝切换**：从AI转到人，要顺畅，别让用户等半天
3. **明确告知**：告诉用户"现在是人工在跟您说话"，别冒充AI
4. **AI辅助人**：人介入的时候，AI可以帮忙整理信息、给出建议，让人效率更高
5. **反馈闭环**：人处理过的案例，可以用来优化AI——下次AI就能自己处理了

---

## 七、行为设计学在AI产品中的应用

### 7.1 点击即承诺（IKEA效应）

**什么是IKEA效应？**
> 用户对自己参与创造的东西，估值更高——哪怕内容完全一样。
> （Norton/Ariely 2012）

**怎么用在AI产品里？**
- 让用户主动点击"生成"按钮——而不是一进来就自动生成
- 让用户做几个简单的选择（风格、场景、偏好）——参与感就上来了
- 让用户可以修改AI生成的内容——改了之后，他会觉得这是"我的作品"

**为什么有效？**
- 主动点击 = 自我筛选 + 承诺仪式
- 用户自己选的，他会更认可结果
- 就算结果一般，用户也会觉得"毕竟是我选的"

**实战案例（穿搭项目）**：
> 购物指南不是自动弹出来的，是用户点"生成购物指南"按钮才生成的。
>
> 为什么？因为点击这个动作本身就是价值——用户主动要的，他会更珍惜、更愿意看。
>
> 如果系统一上来就全给了，用户反而会觉得"反正都是系统生成的，随便看看"。
>
> 这就是"一次全给的隐性代价"——系统全给了，用户的参与感和拥有感就没了。

---

### 7.2 微努力剂量

**什么是"微努力"？**
> 让用户做一点点努力——不能太多（太多了用户会嫌麻烦），也不能太少（太少了没有参与感）。

**甜蜜点：2-4个轻量决策。**

- 1个决策：太少，没有参与感
- 2-4个：刚好——有参与感，又不觉得麻烦
- 5个以上：开始嫌烦了
- 10个以上：放弃走人（摩擦淹没效应）

**反例**：
- 30题的风格测试问卷——用户填到第5题就走了
- 注册要填15个字段——大部分人半途而废

**设计要点**：
- 核心流程的决策点，控制在2-4个
- 更多的设置，放到"高级设置"里——想用的人自己去调
- 能用默认值的，就用默认值——别让用户选

---

### 7.3 效应三前提

IKEA效应不是什么时候都管用的，有三个前提条件：

| 前提 | 说明 | 反例 |
|------|------|------|
| **必须成功完成** | 用户得把事情做成了，才会有成就感 | 等了半天失败了——只会更生气 |
| **必须主动触发** | 得是用户自己主动做的，不是被动的 | 系统自动生成的——跟用户没关系 |
| **必须回显** | 要让用户看到自己的"成果" | 做了选择但看不到效果——等于没做 |

**这三个前提缺了任何一个，效应都会失效，甚至起反作用。**

---

### 7.4 按需索取 vs 一次全给

**两种设计思路**：
- **一次全给**：把所有内容都展示出来，用户想看就看
- **按需索取**：用户点一下，才展开更多内容

哪个好？

**看你的目标是什么**：
- 如果目标是"让用户看到更多内容"——一次全给
- 如果目标是"让用户珍惜内容、提升转化"——按需索取

**为什么按需索取反而转化好？**
- 用户主动要的，他会更认真看
- 有"点击"这个动作，就有承诺感和拥有感
- 交互步骤本身，就是产品价值的一部分

**核心洞察**：
> **系统全给了 → 用户"买不买都行，反正是系统生成的"**
> **按需索取 → 用户"这是我要来的"——他会更重视**
>
> 交互步骤本身，就是产品价值。

---

## 八、自我质疑式设计：怎么避免"想当然"

### 8.1 为什么要自我质疑？

做产品设计最容易犯的错——**想当然**。
- "用户肯定需要这个"
- "这么做肯定更好"
- "逻辑上应该是这样的"

但很多时候，你以为的就是你以为的吗？

**自我质疑，就是故意跟自己唱反调——故意推翻自己的结论，看看是不是真的站得住脚。**

---

### 8.2 自我质疑的方法

#### 方法1：反向推理

> "如果我的结论是错的，最可能是因为什么？"

把你的结论反过来想——如果它不成立，最可能的原因是什么？然后去验证那个原因存在不存在。

如果存在——说明你的结论有问题。
如果不存在——说明你的结论更可靠了。

---

#### 方法2：逐条质疑

把你的设计结论一条一条列出来，然后每条都问：
- 这个结论的前提是什么？
- 前提成立吗？有证据吗？
- 有没有另一种可能？
- 如果前提错了，结论还成立吗？

**实战案例（设计综合v3）**：
> v2版本的结论有三个，v3全部质疑了一遍，结果推翻了两个半：
>
> 1. "共同词表是地基" → 推翻。词表只是"事后校验"路径的前置，不是所有路径的地基。
> 2. "三环节同一根" → 推翻。输入侧缺的和输出侧缺的根本不是同一样东西。
> 3. "输入侧需要词表" → 推翻。输入侧根本不需要词表——LLM直接就能读懂中文描述。
>
> 这三个错误里，第三个最贵——它让"输入侧"这件零依赖的事，看起来依赖"词表"这件重活，从而把优先级完全排反了。

---

#### 方法3：找反例

> "有没有反例？有没有不符合我结论的情况？"

如果你的结论是"所有A都是B"，只要找到一个A不是B，结论就不成立。

找反例是最快的验证方法——只要找到一个反例，你就知道自己错了，赶紧改。

---

### 8.3 验证链：从直觉到决策

这是产品经验里总结的——一个想法从直觉到拍板，要经过6步验证：

```
直觉 → 术语对齐 → 代码对质 → 联网调研 → 低成本实验 → 数据拍板
```

| 步骤 | 做什么 | 目的 |
|------|--------|------|
| **直觉** | 我觉得是这样 | 起点，不是终点 |
| **术语对齐** | 先把词对准了，确保说的是一回事 | 避免鸡同鸭讲 |
| **代码对质** | 去看代码，确认现状 | 避免基于错误的假设讨论 |
| **联网调研** | 看看别人怎么做的、有没有数据 | 借别人的经验 |
| **低成本实验** | 花最小的代价验证一下 | 小成本试错 |
| **数据拍板** | 看实验数据，做决策 | 用数据说话 |

**每往前走一步，你的结论就更可靠一分。**
很多决策，走到第二步第三步就发现错了——省了大量时间和精力。

---

## 九、常见坑 & 避坑指南

### 坑1：为用AI而用AI（锤子找钉子）

**症状**："我们要做AI+XX""大模型这么火，我们也得搞一个"

**后果**：做了个"有AI"的产品，但用户并不觉得更好用。花了很多钱，效果一般。

**避坑**：先想用户痛点，再想解决方案。AI只是工具，不是目的。能用规则解决的，就不用AI。

---

### 坑2：全用大模型，不用规则

**症状**："AI Native嘛，全让大模型生成才够酷"

**后果**：不稳定、贵、慢、不可控。用户体验差，成本还高。

**避坑**：混合架构——规则优先，AI兜底。规则保下限，AI冲上限。能用规则的就用规则，规则搞不定的再用AI。

---

### 坑3：假设AI永远是对的

**症状**：产品设计完全基于"AI输出都是正确的"这个假设，没有任何容错机制。

**后果**：AI一犯错，产品就崩了。用户信任全毁。

**避坑**：假设AI会犯错，然后设计兜底。置信度判断、引用溯源、兜底话术、人工转人工——多重保险。

---

### 坑4：让用户傻等，什么都不显示

**症状**：全屏一个spinner转啊转，用户不知道在干嘛、还要等多久。

**后果**：用户等不及，直接走了。

**避坑**：分层交付——核心内容先出来。显示进度和步骤。60秒以上的，做成后台任务模式。

---

### 坑5：功能堆得越多越好

**症状**："竞品有这个功能，我们也得有""这个功能用户可能会需要"

**后果**：产品越来越复杂，核心功能反而做不好。维护成本越来越高。

**避坑**：少即是多。把核心功能做到极致，比做十个半吊子功能强。每加一个功能，都要问——真的需要吗？有数据支撑吗？

---

### 坑6：只看技术可行性，不看用户价值

**症状**："这个技术很酷，我们做一下""大模型能做XX，我们做个XX功能"

**后果**：做了一堆"技术上很厉害"的功能，但用户并不觉得有用。

**避坑**：从用户价值出发，不是从技术出发。技术再酷，如果用户不需要，那就是没用。

---

## 十一、下一个项目复用检查清单

做下一个AI产品的时候，照着这个清单过一遍设计原则：

### 立项前（场景判断）
- [ ] 痛点强度够吗？（重复性高/人工成本高/规则复杂）
- [ ] 数据可得吗？（知识库/历史数据/标注数据）
- [ ] 容错空间够吗？（有兜底/错了后果不严重）
- [ ] ROI算过吗？（AI成本 vs 收益）
- [ ] 有没有"锤子找钉子"？（是用户需要，还是为了用AI而用AI）

### 架构设计
- [ ] 有没有用混合架构？（规则优先，AI兜底）
- [ ] 哪些用规则？哪些用AI？分清楚了吗？
- [ ] AI输出之后有规则校验吗？（防离谱）
- [ ] 规则部分和AI部分的边界清晰吗？

### 容错设计
- [ ] 置信度判断机制有吗？
- [ ] 引用溯源有吗？（RAG类产品必做）
- [ ] 兜底话术有吗？（答不上来的时候怎么说）
- [ ] 人工兜底机制有吗？（什么时候转人工、怎么转）
- [ ] 多方案对比/可编辑有吗？（推荐/生成类产品）

### 等待体验
- [ ] 生成大概要多久？（测一下，别猜）
- [ ] 等待时长属于哪个区间？（<1s/1-8s/8-20s/20-60s/>60s）
- [ ] 对应的等待体验设计做了吗？（进度/步骤/分层交付）
- [ ] 能分层交付吗？（核心内容先出来）
- [ ] 60s以上的有后台任务模式吗？

### 可解释性
- [ ] 用户能知道"为什么是这个结果"吗？
- [ ] 引用溯源做了吗？
- [ ] 置信度显示了吗？
- [ ] 推理过程需要展示吗？（默认不显示，可以展开）

### 设计自查
- [ ] 有没有想当然的设计？（找出来，质疑一下）
- [ ] 核心结论的前提成立吗？有证据吗？
- [ ] 有没有反例？（找一找）
- [ ] 有没有做过自我质疑？（故意推翻自己的结论试试）

## 最后一句话

**最好的AI产品，不是AI用得最多的，而是AI用得最恰到好处的。**

用户不关心你用了多少AI技术。
用户只关心——这个产品好不好用、能不能解决我的问题、值不值得我花时间。

AI只是手段，不是目的。
